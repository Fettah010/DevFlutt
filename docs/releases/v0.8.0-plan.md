## 1. Outcome and success definition

An Android project can opt into bounded background work, local notifications, and Play in-app updates. Each module has typed app-owned boundaries and tests; unselected modules add no files, dependencies, permissions, or behavior. The generator rejects Android-only selections for iOS targets and reports the selected native/permission changes before writing. Repository agents can discover, provision, boot, diagnose, and test against a repeatable Android emulator using the existing Patrol harness.

## 3. Research (Question | Options | Evidence + date | Finding | Decision | Validation)

See [`docs/research/v0.8-android-platform-services.md`](../research/v0.8-android-platform-services.md), checked 2026-10-28. Decisions:

1. Use `workmanager` 0.10.10 for WorkManager-backed deferrable tasks; constraints and retry/backoff are supported but execution is not exact. Its callback contract maps only success (`true`) and retry (`false`); it has no distinct terminal-failure result, so the module documents that boundary rather than inventing a misleading failure mapping.
2. Use `flutter_local_notifications` 22.3.3 for local channels, permission state, and tap handling. Declare `POST_NOTIFICATIONS` only when selected and request only after an explicit user action. Do not include push messaging.
3. Use `in_app_update` 5.0.0 for the official Play API and `url_launcher` 6.3.3 for the store fallback. The adapter is Android-only; Play availability is not locally verifiable.
4. Mark all three modules Android-only for v0.8 and validate module/platform compatibility before file generation. No new ADR is required; the established app-owned adapter pattern is unchanged. Recheck plugin API/build behavior and dependency/license closure before acceptance.

## 4. In scope

- Add opt-in `background-work`, `local-notifications`, and `app-updates` module manifests, generated implementations, tests, module documentation, and dependency-audit entries.
- WorkManager scheduling exposes named tasks, constraints, and backoff/retry behavior through a fakeable boundary; document best-effort scheduling and input-data privacy.
- Local notifications provide channels, explicit permission requests, permission-denied handling, and validated warm/cold-start tap-to-route hand-off.
- Play updates model available/unavailable, canceled, failed, unsupported, and completed outcomes, with a Play Store HTTPS fallback.
- Reject unsupported target-platform/module combinations before generation. Add declarative permission/native-change aggregation to the generation plan and dry-run summary.
- Conditionally generate the notification permission and test the merged release manifest, dependency/file absence, generated project build, and supported compositions.
- Update CI's generated-project matrix, testing/compatibility/module/security/dependency documentation, third-party notices, changelog, and the living report.
- Make the existing emulator workflow agent-discoverable and reproducible: preflight required SDK tools/images, create a dedicated AVD without modifying broken or user-owned AVDs, wait for a healthy boot, hand off to the existing Patrol runner, and provide clear diagnostics and cleanup behavior.

## 5. Out of scope (including features not to be pulled forward)

- Push messaging providers (including Firebase Messaging), remote notification delivery, or credentials.
- Automatic background synchronization of the v0.7 offline sample; no exact-time scheduling promise.
- iOS substitutes, iOS background configuration, or claiming iOS support for these modules.
- Play Console setup, signing, production rollout, mandatory updates, or claims of live Play flow verification without an owner-run internal test.
- Template-copy update automation (roadmap ADR-009), unrelated release-workflow repair, and v0.9 localization/accessibility features.

## 6. Design / architecture (components, boundaries, contracts, fallbacks, ADR links)

- `background-work` is an Android-only adapter over Workmanager and an app-owned task contract. A top-level background dispatcher must remain a Flutter entry point; no UI state, credentials, or implicit network synchronization belongs in the worker.
- `local-notifications` is an Android-only local notification service. Permission prompting is an explicit user action; the notification's internal route target is validated and passed through the existing router for foreground/background/cold-start taps. Push remains a separate future module.
- `app-updates` wraps `in_app_update` behind an app-owned update client. Platform exceptions/results map to typed outcomes. When Play is unavailable or unsupported, provide an HTTPS Play Store listing via `url_launcher`; no remote Dart execution.
- Module manifests own dependencies, platform compatibility, declared native changes, and permissions. The planner aggregates these; `create --dry-run` displays them. Only selected modules set generation flags or add files.
- Android uses plugin-provided native implementations unless a focused proof shows a missing capability; do not add a custom Kotlin bridge speculatively. Relevant existing decisions: ADR-007 privacy defaults and ADR-008 no implicit background sync.

## 12. Security, privacy, accessibility, localization notes

- Worker input is persisted by the platform and must not contain credentials, tokens, or sensitive payloads. Background execution has no implicit API calls or sync behavior.
- `POST_NOTIFICATIONS` is declared only with `local-notifications`; request after explanatory user intent and expose denied/disabled states without retry-prompt loops.
- Notification tap payloads are untrusted input. Accept only validated internal route targets; never treat arbitrary payload strings as executable code or trusted authorization.
- Update fallback uses the generated package ID to construct an HTTPS Play listing. Surface launch failures; do not download or execute code outside Google Play.
- No analytics, FCM, or telemetry is added. No new user data is sent to DevFlutt.
- Localized notification copy and broad accessibility work are deferred to v0.9; v0.8 tests route/permission states and does not add a notification gallery to blank.

## 15. Risks and mitigations; rollback/recovery

| Risk | Mitigation / recovery |
|---|---|
| Plugin API or current Gradle/AGP incompatibility | Resolve and build each generated module as soon as its dependency is added; if unsupported, amend plan with evidence and choose an alternative before broad integration. |
| Android background scheduling mistaken for exact timing | Typed API and docs say best-effort; test constraints/retry behavior, not wall-clock punctuality. |
| Notification permission requested too early or denied path breaks the app | Permission remains an explicit service call; test first-launch silence and denied behavior on API 33+. |
| Unsafe notification payload is navigated | Parse and validate internal routes; test malformed, external, and unknown destinations. |
| Play API errors misrepresented as success | Map platform exceptions/statuses into typed outcomes; real Play validation is an owner action. |
| Plugin dependencies or permissions leak into default projects | Per-module manifests, static absence tests, built matrix, and release merged-manifest audit. |
| CI scanner absent locally or real hardware unavailable | Require CI scanner jobs; mark real-device/Play checks Owner action and block release until evidence is attached. Emulator setup must not silently accept SDK licenses, replace an existing AVD, or claim physical-device/Play evidence. |

Rollback is limited to reverting the in-scope module/generator commits on this branch; preserve all user/worktree changes and do not rewrite or move published history.
