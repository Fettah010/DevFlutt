## 1. Delivered outcome (vs plan)

Four new modules, all opt-in and all selectable with one explicit flag:

- `auth-core` — the provider-neutral contract. `AuthAdapter`, `AuthSession`, `AuthUser`,
  `AuthState`, a sealed `AuthError`, the `AuthCapability` descriptor, the `SessionStore`
  interface with a secure implementation, the single-flight `TokenRefreshCoordinator`, the
  router-redirect helper, and a `FakeAuthAdapter`.
- `auth-rest` — a custom REST/JWT adapter whose endpoints and payload shapes are
  configuration rather than hard-coded.
- `auth-firebase` — a Firebase Authentication adapter behind a provider port, with an inert
  `firebase_options.dart` placeholder.
- `auth-supabase` — a Supabase Auth adapter behind a provider port, with a
  secure-storage-backed session and an inert configuration file.

One shared contract-test suite runs against all three adapters over the capabilities each
adapter implements. The generator gained `--auth` and `--auth-capability`; a selection whose
provider cannot satisfy a declared capability is refused before anything is written.

**Deliberately not delivered, and why:**

- **The authentication form and its states** — the road map puts the form fields and the
  empty/error/loading/offline states in v0.8.0, "polished UI states". The template has no
  login route, so it cannot ship a login screen without inventing a route the application
  owns. The redirect, the contract, and the failure taxonomy ship now. See
  `docs/DEFERRED.md`.
- **Social sign-in, multi-factor authentication, phone sign-in, anonymous sign-in** — each
  needs provider-console setup and platform configuration the template cannot exercise or
  verify. The capability descriptor reports them unsupported, and calling one raises a
  typed `AuthError.unsupportedCapability` instead of failing obscurely.
- **The data-backend adapters** — Firestore, Postgres, Storage, Realtime, and Edge Functions
  are not in the v0.5.0 Implement list. ADR-006 reserves the `--backend` name so the
  milestone that adds them does not overload `--auth`.
- **The live provider flows** — no Firebase or Supabase project, credential, or redirect
  allow-list was available. Every provider behaviour in this release is contract-tested
  against a fake, and the claim ledger says so. Owner actions OA-6 and OA-7.

## 3. Research and ADR decisions (incl. rejected alternatives)

The full research record is in `docs/releases/v0.5.0-plan.md` §3 (Q1–Q8) and in
`docs/adr/ADR-006-auth-and-backend-adapters.md`. The material decisions:

- **The contract is one interface plus typed errors**, mirroring the `ApiClient` / `ApiError` /
  `ApiResult` trio the template already ships. Exposing the provider SDK types was rejected:
  it would make the contract change with the provider, which is the exact outcome this
  milestone exists to prevent.
- **All three adapters ship.** The exit criteria say "each adapter", and shipping one would
  leave the milestone's own criteria unmet.
- **The auth decision and the backend decision are separate.** `--backend` has never shipped,
  so `--auth` is new surface rather than a break, and ADR-006 reserves the name.
- **The refresh is a single-flight coordinator in `auth-core`**, reused by `auth-rest`. The
  Firebase and Supabase SDKs own their refresh, and the adapter documentation says so rather
  than pretending the template controls it.
- **The Supabase session is persisted through secure storage**, not through the package's
  `shared_preferences` default, because the session carries the refresh token and the
  preferences file is auto-backed-up.
- **The provider configuration is an inert placeholder, not a generated real file.** The
  provider's own tooling writes the real one, and the template fails fast while the
  placeholder is in place.
- **Rejected: `--backend` as one overloaded flag** (the road map forbids it), **a
  home-grown token protocol** (forbidden), **exposing the SDK types** (see above), **the
  Supabase 3.0.0 pre-release** (a pre-release needs a documented material benefit and a
  fallback, and there is neither).

## 5. Matrix coverage actually exercised (method, cases run, gaps)

**Method.** The static matrix enumerates the selections the validator accepts and the
selections it must reject. The built matrix generates, resolves, format-checks, analyzes,
tests, and builds a release APK for each entry, then inspects the merged release manifest.

| Entry | Selection | analyze | test | release APK | merged manifest |
|---|---|---|---|---|---|
| `blank` | `blank` | pass | 17 | 41.9 MB | no INTERNET |
| `core` | `core` | pass | 48 | 45.2 MB | no INTERNET |
| `demo` | `demo` | pass | 37 | 46.9 MB | no INTERNET |
| `recommended` | `recommended` | pass | 79 | 45.8 MB | INTERNET |
| `auth-rest` | `core` + `--auth rest` | pass | 124 | 45.8 MB | INTERNET |
| `auth-firebase` | `core` + `--auth firebase` | pass | 100 | 47.0 MB | INTERNET, plus the provider's own `ACCESS_NETWORK_STATE` and `READ_GSERVICES` |
| `auth-supabase` | `core` + `--auth supabase` | pass | 99 | 49.1 MB | INTERNET |

**Rejections verified.** An unknown provider, two providers at once, an unknown capability, a
capability the chosen provider does not implement, and a capability with no provider
selected are each refused with a non-zero exit code and an actionable message, before
anything is written.

**The gap.** The matrix covers the four presets and the three authentication presets. It does
not cover every combination of the modules that can coexist, and it does not cover the
maximum-capability composition. The exhaustive pairwise set is v0.9.0 work and is recorded
in `docs/DEFERRED.md`. The `auth-core` module on its own, with no adapter, is not built as a
separate matrix entry: it has no provider to exercise, and its own tests run inside every
adapter entry.

## 6. Performance and size (hardware labelled: real vs proxy)

Measured on the build host — Windows 11, Flutter 3.47.5, release builds, fat APK with every
ABI. These are **proxy** figures: no device was involved, and no startup or memory
measurement was taken.

| Entry | Release APK | Difference from the `recommended` baseline |
|---|---|---|
| `recommended` (the v0.4.0 baseline) | 45.8 MB | - |
| `auth-rest` | 45.8 MB | 0.0 MB (0.0 %) |
| `auth-firebase` | 47.0 MB | +1.2 MB (+2.6 %) |
| `auth-supabase` | 49.1 MB | +3.3 MB (+7.2 %) |

The growth comes from the provider SDKs' native libraries: the Firebase Android SDK and the
`app_links` and `url_launcher` plugins the Supabase client brings. The measurement is a
single build-host reading of a fat APK, with no per-ABI split and no per-module breakdown, so
no "lightweight" claim is made about any adapter. Both differences are below the 10 %
investigation threshold. The `auth-rest` adapter adds no dependency at all: it reuses the
`networking` module's `dio`.

Startup time was not measured. The v0.9.0 milestone establishes the startup baseline.

## 7. Security, privacy, dependencies, licenses

| Dependency | Version | Licence | Why |
|---|---|---|---|
| `firebase_core` | `^5.0.0` | BSD-3-Clause | required by `firebase_auth` |
| `firebase_auth` | `^7.0.0` | BSD-3-Clause | the Firebase adapter |
| `supabase_flutter` | `^2.18.3` | MIT | the Supabase adapter |

`supabase_flutter` brings `app_links`, `shared_preferences`, `url_launcher`, `supabase`, and
`supabase_common` with it. The `shared_preferences` dependency is a consequence of the
package's structure: the session is not stored there, but the package still depends on it.
That is recorded rather than hidden. The `supabase_flutter` 3.0.0 pre-release is rejected.

- The secret scan is clean over the whole history, after the one real finding it produced
  (E-018) was fixed and covered by a narrow, commit-scoped allowlist entry.
- The dependency audit is clean over both lockfiles.
- The licence inventory covers every locked package.
- The `INTERNET` permission is the only permission the template itself declares, and only
  for a module that ships a network client. The Firebase Android SDK contributes
  `ACCESS_NETWORK_STATE` and `READ_GSERVICES` from its own manifest; those are the
  provider's, and they are visible in the merged manifest.
- No provider SDK type reaches a feature. No token reaches a log sink. A session's
  `toString` carries no token. The `auth-rest` traffic goes through the same redactor as the
  rest of the client.
- The `publishable key` is public by design; the service-role key and the Firebase
  service-account key are secrets and must never appear in an application.

## 11. Reproduction and recovery instructions

**Reproduce the local gate**

```bash
export PATH="$PATH:/path/to/flutter/bin:/path/to/android-sdk/platform-tools"
./tool/verify/verify.ps1        # or tool/verify/verify.sh
```

**Reproduce the built matrix**

```bash
dart run tool/ftemplate_cli/bin/ftemplate.dart create \
  --name "Gate App" --org com.example --preset core --auth firebase \
  --output /tmp/gate-auth-firebase
cd /tmp/gate-auth-firebase
flutter pub get
dart format --output=none --set-exit-if-changed lib test
flutter analyze --fatal-infos
flutter test
flutter build apk --release --flavor prod
"$ANDROID_HOME"/build-tools/36.0.0/aapt2 dump permissions \
  build/app/outputs/flutter-apk/app-prod-release.apk
```

**Recovery**

- A failed adapter build: the failure is in the generated project, not in the generator.
  Regenerate and read the analyzer output; the adapter's SDK wrapper is the only file that
  imports a provider SDK, so a provider API change is fixed in one file.
- A failed contract test: the shared suite is the contract. A failure in one adapter and not
  in another is an adapter defect; a failure in all three is a contract defect.
- The secret scan turning red on a placeholder: reshape the placeholder so it cannot be
  mistaken for a credential, rather than widening the allowlist.
