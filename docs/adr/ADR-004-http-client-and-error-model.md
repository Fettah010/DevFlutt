# ADR-004: HTTP client, error model, retry policy, cache policy, and token refresh

- Status: Accepted
- Date: 2026-10-22
- Deciders: DevFlutt maintainers

## Context

v0.4.0 introduces the template's transport layer. A generated project that selects the networking
module must be able to call a REST API through a contract that features can depend on, without
leaking transport-specific response details into the UI.

The roadmap requires, explicitly:

- a typed API/error layer that hides transport-specific response details from features (§5.4);
- defined timeouts, cancellation, request IDs, safe log redaction, and retry behaviour (§5.4);
- retry only for appropriate idempotent requests, with no automatic replay of non-idempotent
  operations (§5.4);
- a concurrency-safe token refresh that cannot start many refresh requests or loop indefinitely
  (§5.4);
- no caching of authenticated or sensitive responses without an explicit policy, and a cache must
  state expiration, invalidation, offline behaviour, and what is safe to persist (§5.4);
- a predictable result/error contract — typed success/failure values or well-defined exceptions,
  not a maze of wrapper abstractions (§5.4).

The transport must also be replaceable: an adapter boundary is what lets the auth adapters of
v0.5.0, and any future backend, be added without editing feature code.

## Options considered

1. **Dio (`package:dio`)** — a feature-rich HTTP client with an interceptor chain, a cancellation
   token, per-request timeouts, and pluggable adapters and transformers. Version 5.11.1, published
   2026-09-04, MIT, Dart `>=2.18.0 <4.0.0`, pure Dart (no native code, no Android permission,
   no APK surface). Dependencies: `async`, `collection`, `dio_web_adapter`, `http_parser`, `meta`,
   `mime`, `path`.
2. **`package:http`** — the Dart SDK team's minimal client. Version 1.6.0, published 2025-11-10,
   BSD-3-Clause, Dart `^3.4.0`. Excellent for simple calls, but it offers no interceptor model and
   no cancellation token.
3. **A hand-rolled wrapper over `dart:io` `HttpClient`** — no dependency, full control, but the
   template would own TLS configuration, redirect handling, connection pooling, and timeouts
   itself. That is a security surface the template should not take on.
4. **Dio plus a retry package (`dio_smart_retry`)** — the retry policy would live in a third-party
   package.

## Decision

Use **Dio**, confined to a single file in the generated project, and put every behaviour the
roadmap asks for behind an app-owned `ApiClient` interface.

**Client.** `ApiClient` exposes request/response methods in app-owned types (`ApiRequest`,
`ApiResult<T>`). `DioApiClient` is the only file that imports `dio`. A `FakeApiClient` ships in the
same module so that every behaviour is testable without a live service.

**Error model.** `ApiError` is a sealed type with `network`, `timeout`, `cancelled`, `http`,
`malformed`, and `unknown` cases. Transport exceptions never escape the adapter. The HTTP error case
carries the status code and a short reason, but **not** the response body, because a body may
contain personal data; the body is reachable only through a separate, explicitly requested
accessor. `ApiResult<T>` is the success/failure pair returned to features.

**Timeout and cancellation.** Every request has a connect, send, and receive timeout, configured per
client from `AppConfig`, and every request accepts a cancellation token. A cancelled request
resolves to `ApiError.cancelled` — never to a timeout and never to an unhandled exception.

**Request correlation.** Every request carries an `X-Request-Id` generated by a
`RequestIdFactory`. A retried request reuses the same id so the backend can correlate the attempts.

**Retry.** A `RetryPolicy` is configured on the client, and the default configuration retries
idempotent requests up to three times. `RetryPolicy.none` disables retrying entirely. Only `GET`,
`HEAD`, and `OPTIONS` are eligible. `POST`, `PUT`, `PATCH`, and `DELETE` are never retried
automatically, because the template cannot know whether the backend supplies an idempotency key.
Retry is bounded: at most 3 attempts, exponential backoff capped at 30 s, and a total elapsed
budget of 60 s. Exhaustion produces a typed error, never an exception. The policy is implemented in
the template rather than delegated to a third-party retry package, because idempotency is an
application decision that a transport-level default would get wrong.

The retry loop lives in a `RetryingApiClient` decorator **above** the transport, not inside the
Dio adapter. That is what makes the retry rules — the attempt bound, the idempotency rule, the
timeout budget, the cancellation rule — testable with a fake client and no network at all.

**Cache.** No response caching ships in v0.4.0. Caching authenticated or sensitive responses
requires a policy that states expiration, invalidation, offline behaviour, and what is safe to
persist; there is no authenticated traffic yet, and a cache added now would be a guess. The policy
is deferred to v0.6.0 with the persistence and offline modules.

**Token refresh.** No refresh code ships in v0.4.0 — there is no auth adapter yet. The shape is
fixed here so the v0.5.0 implementation cannot drift: refresh lives behind a single
`TokenRefresher` seam; concurrent callers that observe an expired token share **one** in-flight
refresh; a failed refresh signs the session out rather than retrying; and a refresh that fails
while another caller is waiting fails all of them exactly once. `POST`-shaped refresh calls are
excluded from the generic retry policy, because a refresh is not idempotent by default.

## Evidence

- `dio` 5.11.1 on pub.dev, published 2026-09-04, MIT licence, Dart `>=2.18.0 <4.0.0`, 151
  published versions, 4.99M downloads, verified publisher `flutter.cn` (checked 2026-10-22).
- `http` 1.6.0 on pub.dev, published 2025-11-10, BSD-3-Clause, Dart `^3.4.0` (checked 2026-10-22).
- Flutter stable 3.47.3 ships Dart 3.13.3 and satisfies both SDK constraints (checked 2026-10-22).
- Dio's documented interceptor, `CancelToken`, and timeout APIs (pub.dev, checked 2026-10-22).
- The roadmap's own candidate table names Dio as the HTTP candidate default, with the instruction
  to "hide it behind app-owned API types" (§13).

## Trade-offs

- Adds `dio` and its seven transitive dependencies to generated projects that select the
  `networking` module. All are permissively licensed.
- Dio's API surface is much larger than the template uses. The mitigation is structural: one file
  imports it, and the app-owned interface is the only thing features see.
- The `http` package would have kept the dependency graph smaller, at the cost of hand-building
  cancellation, correlation, and retry — the three behaviours the milestone is actually about.
- The retry ceiling (3 attempts / 60 s) is a template default, not a law. It is expressed in
  `RetryPolicy` so a project can widen it deliberately.

## Consequences

- The `networking` module owns `ApiClient`, `ApiResult`, `ApiError`, `ApiRequest`,
  `ApiCancellationToken`, `RetryPolicy`, `RetryingApiClient`, `DioApiClient`, `FakeApiClient`, and
  `RequestIdFactory`.
- Features depend on `ApiClient` and `ApiResult`, never on `dio`. A `package:http` adapter can be
  added later without touching feature code.
- `API_BASE_URL` (already a configuration key of `architecture-core`) is the only configuration the
  module consumes; the networking module adds no new configuration key.
- The `networking` manifest declares `privacy.network: true`; it is never part of `blank` or `core`.
- The template pins `dio` to `^5.11.1` in `manifests/modules/networking.yaml` and re-verifies it at
  each release gate.

## Revisit triggers

- Dio is unmaintained, publishes a major version that changes the interceptor, cancellation, or
  timeout API used here, or its licence changes.
- A generated project's dependency budget cannot absorb Dio's transitive set, and the
  `package:http` adapter proves sufficient for real use.
- A future milestone needs HTTP/2, connection pooling, or upload progress that the chosen
  transport does not provide.
- The v0.5.0 auth work shows that the `ApiClient` interface is missing a capability that a
  provider adapter requires — in particular per-provider base URLs or per-request signing.
