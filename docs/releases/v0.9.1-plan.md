## 1. Outcome and success definition

The generator offers one explicit data-backend choice independently from authentication:
`none`, `rest`, `firebase`, or `supabase`. `rest` uses the existing `networking` module;
`firebase` selects the Firestore data capability; `supabase` selects the Postgres/PostgREST
data capability. Provider-specific modules expose provider-specific clients and contracts.
There is no universal database/backend abstraction, and selecting a backend does not silently
select an authentication provider.

Add the roadmap's `commerce` and `full` presets before the v0.10 feature freeze. Presets
remain explicit module sets: `commerce` combines the recommended foundation with the catalog,
cart, and local cart persistence; `full` composes all mutually compatible, non-provider modules
for Android. Provider and auth choices remain explicit additions.

This milestone does not claim live service operation without provider credentials. It does
prove that each selected generated project resolves, analyzes, tests, and builds, that provider
initialization is shared when a matching auth and data module coexist, and that absent modules
leave no output residue.

## 3. Research and decisions (checked 2026-11-01)

1. **Keep the provider packages already used by the template.** `supabase_flutter ^2.18.3`
   already builds in the generated auth-Supabase matrix and directly exposes the Postgres
   client. A scratch project using the same package set resolved, analyzed, and built Android
   debug without Firestore. No additional Supabase runtime package is needed.
2. **Use Firestore 7.1.0 only with a narrow generated-project Gradle hook.** The package
   metadata requires `firebase_core ^5.1.0`, compatible with the existing Firebase Auth
   `firebase_core ^5.0.0` constraint. Its Android Gradle project omits a namespace and fails
   under AGP 9.1.0. A typed root-project `plugins.withId("com.android.library")` hook scoped
   to `cloud_firestore` supplies the package's manifest namespace before variant creation;
   the unmodified package then passed clean debug and release builds with the repository's
   existing Kotlin safeguards. No patch to Pub cache or third-party source is allowed.
   Record the hook as an isolated compatibility workaround and retain a regression build.
3. **Share provider initialization without coupling auth to data.** Introduce provider-core
   support modules for Firebase and Supabase. Auth and data modules require the matching core,
   which owns provider configuration and initializes each SDK once. Supabase core defaults to
   non-persistent auth storage; when `auth-supabase` is selected, startup supplies its existing
   secure-storage-backed persistence. Firebase auth and Firestore reuse the same inert
   `DefaultFirebaseOptions` placeholder and `Firebase.initializeApp` call.
4. **Do not implement every service in either provider.** Firebase Firestore and Supabase
   Postgres/PostgREST are the data capabilities in scope. Firebase Storage/Realtime/Analytics
   and Supabase Storage/Realtime/Edge Functions/Analytics remain deferred. The module docs
   must state each provider's security rules, authorization, pricing, offline, and live-test
   responsibilities.
5. **Keep the existing `demo` preset contract intact.** Add `commerce` and `full` without
   repurposing `demo`; the full preset is Android-only because it includes Android platform
   services. No backend or auth provider is implicit in a preset.
6. **Stage generated output on its destination volume.** The CLI previously generated in
   `Directory.systemTemp` and renamed files into the requested output. On this Windows host
   system temp is on D: while the repository/output is on C:, so generation failed with
   Windows error 17. Generate staging under the nearest existing output ancestor, then
   rename the completed project directory as one unit; cover this with a CLI regression test.

The namespace proof is a compatibility result for the pinned toolchain, not evidence that the
upstream Firestore package has fixed its Gradle metadata. Re-check the plugin and remove the
hook only after an upstream release proves the namespace is present on the supported matrix.

7. **Honor the device theme and test it without OEM-setting assumptions.** Android's
  [dark-theme guidance](kb://android/develop/ui/views/theming/darktheme), checked 2026-11-01,
  says Android 10+ system dark theme applies to apps and recommends system default. Flutter
  3.47.9's `MaterialApp` source defaults `themeMode` to `ThemeMode.system`. On the Redmi 8 /
  Android 10 / MIUI V125, Patrol's `disableDarkMode()` and direct `cmd uimode night no` both
  returned without changing the device's reported dark mode; the app's dark appearance matched
  that device state. Make system mode explicit in reference and generated apps, assert the
  actual device brightness in Patrol, and test dark/light changes deterministically through
  Flutter's `TestPlatformDispatcher` in widget tests. This retains meaningful coverage without
  assuming an OEM honors test-runner shell commands.
8. **Separate physical-device measurement from APK installation.** The Redmi's MIUI
  installer prompt is a device security control; two observed smoke retries timed out with
  `INSTALL_FAILED_USER_RESTRICTED`, and the “Remember my choice” control was disabled in the
  captured dialog. Do not automate its approval or change MIUI security settings. Android's
  [ADB documentation](https://developer.android.com/tools/adb) describes device-side
  authorization as a user-acknowledged protection; the official
  [dumpsys documentation](https://developer.android.com/tools/dumpsys) documents app frame
  diagnostics via `gfxinfo`/`framestats` and process memory via `meminfo`; Android's
  [startup guidance](https://developer.android.com/topic/performance/issues/launch-time)
  defines TTID as the time to the first UI frame. Build an install-free measurement probe
  that verifies the exact installed APK, then force-stops and launches it, recording the
  matching `ActivityTaskManager` `Displayed` TTID event plus `am start -W`, PSS, and
  `gfxinfo` frame counts. If the exact package/artifact is absent or mismatched, fail with a
  clear manual-install prerequisite and make no install attempt. Treat launch-only frame
  data as descriptive, not representative animation jank; report missing frame data as
  unavailable, never as zero. Keep Patrol UI tests on the emulator for repeatability; the
  earlier manually approved Redmi Patrol pass remains the physical-device smoke evidence.

## 7. Performance, security, dependencies, and privacy

No performance budget is added; collect artifact sizes for the new provider combinations as
descriptive data for v0.10 baselines. Pin package lower bounds to the verified compatible
constraints and update the optional-module dependency union and third-party notices. Firebase
configuration remains inert until `flutterfire configure`; Supabase uses only its public
publishable key. Never include a service-role key, private Firebase key, or user data in
generated files or tests. Document Firestore/Supabase server authorization and pricing
responsibilities. Do not claim test-fake results as live provider evidence.

## 8. Risks and recovery

| Risk | Mitigation / recovery |
|---|---|
| Upstream Firestore Gradle metadata changes and the workaround becomes invalid | Keep a focused generated build regression on the pinned AGP; fail loudly; remove the hook only after an upstream package build proves it unnecessary. |
| Provider auth/data modules initialize twice or overwrite shared configuration | Provider-core module owns config and initialization; test every matching pair and generate one copy only. |
| Supabase defaults persist a refresh token in ordinary preferences | Supabase core defaults to `EmptyLocalStorage`; Supabase Auth explicitly supplies secure storage; source and tests assert the distinction. |
| Multiple backend choices imply false parity | Expose capability-specific provider modules and provider-specific APIs; no universal CRUD abstraction; document exact supported service. |
| New full preset creates native/permission conflicts | Resolve through the existing graph before generation; test Android-only constraint and release manifest; do not silently drop a module. |
| Provider packages change before release | Recheck package version, license, advisories, Kotlin/AGP compatibility, and API behavior at V2 and V3. |

Rollback only v0.9.1 changes on this isolated branch. Preserve the original checkout, all
published refs, and all user changes.
