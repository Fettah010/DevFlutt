## 4. Verification strategy

- Cheapest first: format → analyze → focused Flutter tests → existing full verification script → Patrol test target(s) on a named emulator.
- CI runs a dedicated emulator-backed Patrol workflow with a clear smoke subset and a separate complete suite; collect Patrol reports, screenshots/videos where supported, emulator configuration, and logcat on failure.
- No `|| true`, blanket `continue-on-error`, or empty/fake assertions. If host cannot run an emulator, local status remains unverified and CI is required for V2/V3.
- The historical generated-project version matrix is not required by roadmap v0.6.0 and currently tests a synthetic widget. Replace with an honest deferred item; generated-project E2E coverage remains scheduled for the later matrix milestone unless it can be made to test real generated output within this plan.

## 8. Risks and plan decisions

| Risk | Mitigation |
|---|---|
| Existing host cannot run Flutter/adb because user-home configuration is broken | Redirect Android user/cache paths to a workspace or temp directory and retry; if still blocked, CI emulator evidence is required and local device status is reported as unavailable. |
| Emulator-dependent native actions vary by API/system image | Pin the CI API/image and use one emulator per job; report exact matrix and avoid claiming physical-device coverage. |
| Tests mutate persistent emulator settings and contaminate subsequent tests | Use Patrol full isolation or explicit setup/cleanup; avoid tests that cannot restore global state. |
| The original v0.6 persistence scope conflicts with the paused local v0.6 Patrol work | User explicitly requested continuation of Patrol first. The roadmap now reschedules persistence as v0.7.0 and shifts later pre-1.0 milestones; no planned outcome is removed. |
