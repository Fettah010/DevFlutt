## Android

The Android-only `background-work`, `local-notifications`, and `app-updates` modules are
rejected for unsupported target platforms before generation. `background-work` declares
the WorkManager boot, wake-lock, and network-state permissions and removes the plugin's
unused foreground-service permissions. `local-notifications` alone declares
`POST_NOTIFICATIONS` and `VIBRATE`, and enables core-library desugaring required by its
plugin. The notification permission is requested at runtime only after an explicit
application action.
`app-updates` requires an installation distributed through Google Play for Play availability
and update flows to work. Its HTTPS listing fallback can be used when the Play API is
unavailable; the module does not add the `INTERNET` permission.

The template targets Android API 24 or newer. The `INTERNET` permission is declared only by
selected modules that need network access, including `networking`, the Firebase and
Supabase provider/auth modules, and is written into the main manifest so release builds can
reach their services. A project that selects none of them declares no app-owned network or
optional runtime permission. The `INTERNET` permission is a normal install-time permission
and raises no runtime prompt.
The AndroidX app-scoped `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` may also appear in every
merged release manifest; it is generated by the platform dependencies and is not an
optional-module runtime permission.

The Firebase Android SDK contributes `ACCESS_NETWORK_STATE` and `READ_GSERVICES` from its
own manifest. Those are the provider's permissions, not the template's, and they are visible
in the merged release manifest of an `auth-firebase` or `backend-firestore` project.

- Conservative Kotlin flags (`android.builtInKotlin=false`, `android.newDsl=false`,
  `android.enableIncrementalKotlin=false`, `kotlin.incremental=false`) are used because of
  flutter/flutter#192167 (built-in Kotlin validation fails on AGP 9.1+) and to avoid
  Kotlin incremental-cache corruption on generated-project Gradle runs.
- The release manifest requests `INTERNET` only when selected modules need network access
  (`networking`, `auth-firebase`, `auth-supabase`, `supabase-core`, or
  `backend-firestore`). CI verifies that match with `aapt2 dump permissions`.
- Every environment is an Android product flavor: `dev`, `staging`, and `prod`. The flavor
  decides the application ID suffix (`.dev`, `.staging`, none) and the launcher label.
- Because flavors are defined, an Android build must name one: `flutter build apk --flavor dev`.
  Without `--flavor`, the Flutter tool cannot pick a variant.

`go_router` 18 migrated to the `material_ui` and `cupertino_ui` packages internally. The public
API used by the template (`GoRouter`, `GoRoute`, `GoRouterState`) is unchanged, and generated
applications still import `package:flutter/material.dart`.

Riverpod 3 moved `StateProvider` and `StateNotifierProvider` to
`package:flutter_riverpod/legacy.dart`. The template uses `Notifier` and `NotifierProvider`, so no
generated project depends on the legacy library.

`dio` 5.11.1 is pure Dart, so it adds no Android native code, no permission, and no APK
surface. `flutter_secure_storage` 11.2.0 needs Android API 23 or newer; the template uses
`minSdk 24`. Both are `^`-ranged in a generated project, and the generated project's lockfile
is the developer's to commit.

`firebase_auth` 7.0.0 and `firebase_core` 5.1.0 need Android API 24 or newer, which is
exactly the template's `minSdk`. Both still apply the Kotlin Gradle Plugin, and Flutter 3.47
warns that future Flutter versions will refuse plugins that apply it. Generated Firebase
Auth debug and release builds succeed on the pinned toolchain, and the warning is recorded
rather than hidden. `firebase_core` is supplied by `firebase-core` so Firebase auth and data
modules share one configuration and initializer.

`supabase_flutter` 2.18.3 needs Flutter 3.35 or newer and brings `app_links`,
`shared_preferences`, `url_launcher`, and `supabase` with it. The 3.0.0 pre-release is
rejected: a pre-release needs a documented material benefit and a fallback, and there is
neither. The session is persisted through the template's secure store rather than the
package's `shared_preferences` default, but `shared_preferences` remains a transitive
dependency of the package. `supabase-core` uses `EmptyLocalStorage` when no Supabase Auth
module is selected; Supabase Auth supplies secure storage when it is present.

`cloud_firestore` 7.1.0 currently omits its Android namespace under AGP 9.1.0. The generated
root Gradle build adds a typed namespace hook scoped to the `cloud_firestore` subproject
only when `backend-firestore` is selected. That module is Android-only until iOS generation
and builds are verified.

## Generation matrix

The checked-in [`generated_project_matrix.json`](../tool/verify/generated_project_matrix.json)
is the source for 25 required CI cases. A validator rejects missing, unexpected, duplicate,
malformed, or misconfigured entries—including incorrect module selections and permission
expectations—before matrix expansion. Each generated project is resolved,
formatted, analyzed, tested, and built in Android debug and release; the matrix also checks
release permissions and selected native components. The test-event guard rejects zero-test,
skipped, or unsuccessful runs, and CI uploads per-case test and release-manifest reports.

| Coverage group | Required cases | Current evidence |
|---|---|---|
| Named presets | `blank`, `core`, `demo`, `recommended`, `commerce`, `full` | Existing four presets have prior matrix evidence; `commerce` and `full` were locally generated, resolved, formatted, analyzed, tested, and debug/release built. Current-branch CI is pending. |
| Localization | `demo` + `localization` | Previously exercised in the generated-project matrix; current-branch CI is pending. |
| Auth alone | `auth-rest`, `auth-firebase`, `auth-supabase` | Prior generated-project evidence; current-branch CI is pending. |
| Backends alone | `--backend rest`, `firebase`, `supabase` | Firestore and Supabase data-only builds were verified locally; explicit backend-selection matrix cases await CI. |
| Matching auth/data | Firebase Auth + Firestore; Supabase Auth + Postgres/PostgREST | Supabase Auth + data has prior local generated-project evidence; Firebase pair awaits CI. |
| Maximum Android composition | `full` + Firebase Auth + Firestore | Required CI case; pending. |
| Standalone modules and platform pair | Preferences, database, offline data, commerce, commerce persistence, background work, notifications, updates, background work + notifications | Prior local/CI evidence as recorded by their milestone reports; current-branch CI is pending. |

This table states the required coverage and its present evidence; it does not mark a
not-yet-observed branch CI run as Verified (CI). The full pairwise set and historical
compatibility regressions remain v0.10.0 work.

## Coverage method

The matrix is exercised in CI on every pull request. Each case is generated into a
temporary directory and then resolved, format-checked, analyzed, tested, and fully built
with debug and release APKs. Individual module manifests are validated separately. The
generator's own tests enumerate acceptance and absence rules for service
and platform modules: a blank project has no optional service files, dependencies,
imports, or module-specific permissions; selected projects receive only their declared
files and native configuration. The maximum-capability Android composition is included in
the v0.9.1 matrix; exhaustive pairwise combinations are scheduled for v0.10.0.

Every auth adapter is verified against one shared contract-test suite. The generated matrix
also verifies each backend alone and the matching Firebase Auth + Firestore and Supabase
Auth + Postgres/PostgREST compositions. The generator's own tests enumerate the selection
rules: an unknown provider is refused, two data providers are refused, an unknown capability
is refused, and a capability the chosen auth provider does not implement is refused with a
message that names the providers that do.

**The gap.** The 25 required cases do not cover every compatible module combination or the
exhaustive pairwise set. That work remains in v0.10.0 and is recorded in `docs/DEFERRED.md`.

## Generator dependencies

The generator package depends on `dart_style` and `pub_semver` in addition to `mason`.
The formatter runs over the generated files so that a generated project is
format-clean without the brick having to encode the formatter's layout rules. These
are generator-only dependencies; a generated application depends on the Flutter SDK
and the modules it selects.

The generator's lockfile is committed so license inventory, generator tests, and the
dependency audit use the same package graph locally and in CI. The
`tool/module_dependency_audit` lockfile is also committed: it is a versioned union of
optional generated-app dependencies, not a reusable-library lockfile.

## Known gaps

- The v0.8 API 33+ emulator and physical-device permission/tap/background smoke, and the
  Play internal-track update test, remain unverified. The local AVD entries could not be
  started because their configuration files contain unresolved placeholders.
- v0.8 release APK sizes are recorded as single-build reference values in the completion
  report; no repeated performance measurement or size budget is claimed.
- iOS build smoke is scheduled for v0.10.0. The three v0.8 modules are Android-only and
  are rejected for iOS before generation.
- The `DioApiClient` error mapping is verified by review and by the contract tests over
  the fake client; the Dio transport itself is not exercised against a live server.
- The live Firebase and Supabase auth flows are not exercised: no provider project was
  available, so every provider behaviour is verified by contract tests over a fake. The
  provider configuration placeholders and the start-up configuration check are verified.
- The 25-case v0.9.1 generated-project matrix includes all six named presets, each data
  backend alone, matching provider auth/data pairs, the maximum-capability Android
  composition, and the standalone module cases. It does not cover every compatible
  combination; the exhaustive pairwise set is v0.10.0 work.
- The generator is a CLI proof of scope; `doctor` and `update-guide` arrive later.
- The release signing configuration is still the debug key; real signing arrives later.
