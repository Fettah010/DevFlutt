## 1. Delivered outcome (vs plan)

Generated `blank`, `core`, and `demo` Flutter projects that share one documented architecture: a
single startup path (`bootstrap()`), a predictable Riverpod container, a go_router router with a
guarded redirect extension point and deep-link/unknown-route handling, a neutral Material 3
token/theme foundation with reusable core widgets, typed environment and flavour configuration,
and a counter feature that shows domain/data/application/presentation placement. The `demo` preset
adds a component showcase. Android builds are per-flavour (`dev`, `staging`, `prod`) with a real
build identity.

Two deviations from the plan, both recorded in the plan's progress log:

- The generator now runs the canonical Dart formatter over the generated files. The brick stores
  Dart as text with conditional sections, so the rendered layout depends on the selected variant.
  Formatting the output removes that fragility and makes every generated project format-clean.
- The `APP_ENV` wire names changed from `development`/`staging`/`production` to
  `dev`/`staging`/`prod` so that they match the Gradle flavour names.

## 3. Research and ADR decisions

- Riverpod chosen (ADR-001). `flutter_riverpod` 3.4.3, published 2026-09-03, SDK `^3.12.0`.
  Riverpod 3 moved `StateProvider`/`StateNotifierProvider` to `legacy.dart`; the template uses
  `Notifier`/`NotifierProvider`, so no generated project depends on the legacy library.
- go_router chosen (ADR-003). `go_router` 18.1.1, published 2026-10-20, Flutter `>=3.44.0`,
  Dart `^3.12.0`. Version 18 migrated internally to `material_ui`/`cupertino_ui`; the public API
  used by the template is unchanged.
- Design tokens: Material 3 `ColorScheme.fromSeed` plus explicit spacing, radius, and motion
  tokens. No new runtime dependency.
- Environments: Gradle product flavours (`dev`, `staging`, `prod`) with an `applicationIdSuffix`
  and a per-flavour `app_name` resource, plus typed `--dart-define` configuration.

## 5. Matrix coverage actually exercised

`blank`, `core`, and `demo` presets fully built in CI (pub get, format check, analyze, test, and
`flutter build apk --debug --flavor dev`). The root reference app is format-checked, analyzed,

validated separately. Pairwise and maximum-coverage combinations are deferred to v0.9.0.

## 7. Security, privacy, dependencies, licenses

- New generator-only dependencies: `dart_style` 3.1.14 (BSD-3-Clause) and `pub_semver` 2.2.1
  (BSD-3-Clause). Generated applications depend on neither.
- `flutter_riverpod` 3.4.3 and `go_router` 18.1.1 are used by the generated `core` and `demo`
  projects; both were re-verified on 2026-10-21.
- No new Android permissions at v0.3.0. The release APK requests no `INTERNET`, verified with
  `aapt2 dump permissions`.
- Configuration error messages never repeat the offending value, so deployment details cannot
  reach logs.

## 8. Accessibility / localization / device evidence

- Generated-project tests cover semantic labels, double text scale without overflow, and the
  distinct semantic colours of the light and dark schemes.
- Device and emulator smoke remain deferred to v0.9.0. No device gate was required at v0.3.0.

## 9. Known issues, deferred work, owner actions

- The release signing configuration is still the debug key; real signing arrives later.
- The brick does not ship the `android/app/src/debug` and `android/app/src/profile` manifests, so
  a generated debug build has no `INTERNET` permission. This keeps the blank-first guarantee for
  debug builds as well as release builds.
- Localization, full accessibility, and reduced-motion handling remain deferred to v0.8.0.
- Owner actions: none required for v0.3.0; branch protection and the template-repository flag
  remain v1.0.0 owner actions.
