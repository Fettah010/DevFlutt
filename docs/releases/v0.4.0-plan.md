## 1. Outcome and success definition

Networked Flutter projects can select a transport, a logger, a secure store, and an error-reporting
interface that all work together without leaking transport details, secrets, or tokens into the UI
or the logs.

Success means:

- A generated project that selects the networking module talks to a REST API through an app-owned
  client interface, with timeouts, cancellation, request correlation, typed error mapping, and
  bounded retry that never replays a non-idempotent request.
- A deterministic fake adapter lets every one of those behaviours be tested with no live service.
- Logs are structured, severity-tagged, category-scoped, and redacted by default; a regression
  corpus proves no token, authorization header, password, or payment-like field reaches a log sink.
- Secure key/value storage is reachable only through a small app-owned interface, backed by a
  maintained plugin, with the platform requirements (including the Android backup requirement)
  generated and documented rather than left to the developer.
- Blank and core presets carry none of these dependencies, and that absence is enforced by tests.
- CI fails on a committed secret or a known-vulnerable dependency.

## 3. Research (Question | Options | Evidence + date | Finding | Decision | Validation)

### Q1 — Which HTTP client sits behind the typed networking layer?

- **Options:** `dio` 5.x · `http` 1.x · a hand-rolled `HttpClient` wrapper · `dio` + `dio_smart_retry`.
- **Evidence (2026-10-22):** `dio` 5.11.1, published 2026-09-04, **MIT** (pub.dev licence page:
  "Copyright (c) 2018 Wen Du (wendux), Copyright (c) 2022 The CFUG Team"), SDK `>=2.18.0 <4.0.0`,
  pure Dart, dependencies `async`, `collection`, `dio_web_adapter`, `http_parser`, `meta`, `mime`,
  `path`; platforms Android/iOS/Linux/macOS/web/Windows; 151 published versions; 4.99M downloads;
  publisher `flutter.cn` (verified). `http` 1.6.0, published 2025-11-10, BSD-3-Clause, SDK `^3.4.0`,
  dependencies `async`, `http_parser`, `meta`, `web`; no interceptor model, no cancellation token.
  Road map §5.4 and §13 both name Dio as the candidate default.
- **Finding:** Dio ships exactly the primitives the milestone requires — an interceptor chain, a
  cancellation token, and per-request timeouts — while `http` would force cancellation, request
  correlation, and retry to be hand-built. Dio is pure Dart, so it adds no Android native code, no
  permission, and no APK surface. `dio_smart_retry` is a third-party retry policy package; the
  retry policy here must be app-owned because idempotency is an application decision, not a
  transport default.
- **Decision:** `dio` `^5.11.1`, used only inside an app-owned `ApiClient` implementation. Retry is
  implemented in the template, not delegated to a package.
- **Validation:** AD-004; unit tests exercise the adapter through a fake transport, so the Dio
  surface used by the template is small and reviewable.

### Q2 — Which secure-storage plugin, and what platform does it require?

- **Options:** `flutter_secure_storage` · `shared_preferences` (insecure) · a bespoke Keystore bridge.
- **Evidence (2026-10-22):** `flutter_secure_storage` 11.2.0, published 2026-09-16, **BSD-3-Clause**,
  verified publisher `steenbakker.dev`, SDK `>=3.8.0 <4.0.0`, Flutter `>=3.19.0`, 66 published
  versions, 5.42M downloads, supports Android/iOS/macOS/Windows/Linux/web. Since v10 it uses its own
  ciphers — RSA-OAEP key cipher + AES-GCM storage cipher by default — and **no longer** uses the
  deprecated Jetpack Security `encryptedSharedPreferences`. **Minimum Android SDK is now 23.**
  The plugin README states that Android auto-backup of the app's SharedPreferences causes
  `java.security.InvalidKeyException: Failed to unwrap key` on restore, and requires either
  disabling auto-backup or excluding the plugin's `sharedpref` file.
- **Finding:** Compatible with this project — the template's `minSdk` is 24 (≥ 23), Dart 3.13.3
  (≥ 3.8.0), Flutter 3.47.3 (≥ 3.19.0). The plugin's v10+ cipher change removes a deprecated
  dependency. The Android backup interaction is a real, documented platform requirement that the
  generator must satisfy, not a note the developer has to discover.
- **Decision:** `flutter_secure_storage` `^11.2.0` behind an app-owned `SecureStore` interface. The
  brick generates the Android backup exclusion when the module is selected and the module README
  states the minimum API level and the backup behaviour.
- **Validation:** AD-004 (interface), the generated-project matrix builds the module, and the merged
  release manifest is inspected for the backup attributes.

### Q3 — How are logs produced and redacted?

- **Options:** the `logging` package · `talker` · a bespoke app-owned logger.
- **Evidence (2026-10-22):** Road map §6.1 requires a `logging` module delivering "structured logs,
  severity, category/request context, debug-only verbosity, redaction helpers" with "secrets,
  tokens, passwords, auth headers, and sensitive payloads redacted by default". Protocol §8.2
  forbids `print` in app code and requires the logging interface.
- **Finding:** The requirement set is narrow and the security-critical part — redaction — must be
  owned and regression-tested by the template. Either third-party package would be wrapped by an
  app-owned interface anyway, adding a dependency and an abstraction layer without removing
  either.
- **Decision:** A bespoke, dependency-free app-owned logger: `AppLogger` interface, `LogLevel`,
  `LogRecord`, `Redactor`, and a `ConsoleLogger` that honours the debug/release verbosity policy.
- **Validation:** Unit tests over a fixed redaction corpus.

### Q4 — How are errors reported?

- **Options:** Sentry / Crashlytics / Firebase Crashlytics SDKs · an app-owned interface only.
- **Evidence (2026-10-22):** Road map §6.1 `diagnostics` module: "Error capture interface,
  user-consented diagnostic sharing where relevant, crash-reporting adapter hooks — no provider SDK
  or outbound telemetry in blank preset". §8.4: "No telemetry without explicit configuration".
- **Finding:** The milestone text asks for "app-owned error reporting interfaces; keep actual
  crash/analytics providers optional and separately selectable". Shipping a provider SDK would add a
  native dependency, a permission surface, and an outbound data path that the milestone forbids by
  default.
- **Decision:** Ship the `ErrorReporter` interface and a local, in-memory `LocalErrorReporter`
  adapter. No provider SDK, no analytics, no outbound traffic. Provider adapters are deferred.
- **Validation:** The blank/core presets contain no diagnostics SDK; the module's tests assert that
  the local adapter never touches the network.

### Q5 — Which secret-scanning tool runs in CI?

- **Options:** `gitleaks/gitleaks-action` v2 · the `gitleaks` binary run directly · TruffleHog.
- **Evidence (2026-10-22):** `gitleaks` v8.30.1, MIT, Go, ~30.1k stars, most recent release
  2026-03-21, last commit 2026-09, "security-patch-only" posture (the README opens with a
  "feature complete" notice). The **action** changed from MIT to a proprietary licence in v2.0.0
  and **requires a `GITLEAKS_LICENSE` key for organisation-owned repositories**; it also pulls an
  unpinned container image. TruffleHog is AGPL-3.0.
- **Finding:** The scanner itself is permissively licensed and maintained. The *action* introduces
  a licence obligation and an unpinned image for a personal repository that does not need either.
  Running the pinned binary directly, with a published-checksum verification step, is licence-free
  for this repository and reduces supply-chain surface.
- **Decision:** CI downloads a pinned `gitleaks` release, verifies its published SHA-256 checksum,
  and runs it with `--redact`. No third-party action is used.
- **Validation:** The CI job must be observed to go red on a deliberately committed canary secret
  (gate self-test, §9.2) and green on the real repository.

### Q6 — Which dependency-vulnerability scanner runs in CI?

- **Options:** OSV-Scanner · `dart pub outdated` alone · Dependabot only.
- **Evidence (2026-10-22):** `osv-scanner` v2.7.0, published 2026-10-12, **Apache-2.0** (Google),
  supports `pubspec.lock` as a first-class lockfile, and v2.7.0 enables the Dart
  `package_config.json` extractor by default for lockfile scans. The Dart SDK itself uses
  OSV-Scanner in its own third-party dependency workflow.
- **Finding:** OSV-Scanner consumes the lockfiles this repository already commits, so no new
  resolution step is needed. `dart pub outdated` reports newer versions, not vulnerabilities.
- **Decision:** CI downloads a pinned `osv-scanner` release, verifies its published checksum, and
  scans the reference app's `pubspec.lock` and the generator's `pubspec.lock`.
- **Validation:** Gate self-test with a deliberately vulnerable lockfile entry is **not** practical
  (it would pollute the lockfile), so the job is instead proven by observing it execute and report
  zero findings, and by a local run against a throwaway project with a known-vulnerable dependency.

### Q7 — How is the licence inventory produced?

- **Options:** a hand-maintained list · a tool that queries the pub.dev API for each locked package.
- **Evidence (2026-10-22):** Protocol §10 requires "an auditable inventory
  (`THIRD-PARTY-NOTICES.md` plus dependency review notes)" with, per dependency, purpose, version,
  upstream URL, licence source, and compatibility notes.
- **Finding:** A hand-maintained list drifts silently from the lockfile. The lockfile already names
  every package and version; the licence is one API field away.
- **Decision:** A repository tool reads `pubspec.lock`, queries the pub.dev API for each package's
  licence and homepage, and regenerates `THIRD-PARTY-NOTICES.md`. CI re-runs it and fails if the
  committed file differs.
- **Validation:** The tool's own unit test; the CI check must be observed to fail on a stale file.

## 6. Design / architecture

### 6.1 Module surface

```text
lib/core/logging/            (module: logging)
  app_logger.dart            AppLogger interface, LogLevel
  log_record.dart            LogRecord (message, level, category, fields, timestamp)
  redactor.dart              Redactor — key-based and value-pattern redaction
  console_logger.dart        ConsoleLogger — debug/release verbosity policy
  memory_logger.dart         MemoryLogger — test sink that captures records

lib/core/networking/         (module: networking)
  api_client.dart            ApiClient interface (app-owned)
  api_error.dart             ApiError — sealed: timeout, cancelled, network, http, malformed, unknown
  api_result.dart            ApiResult<T> — success | failure
  api_request.dart           ApiRequest (method, path, body, headers, query)
  retry_policy.dart          RetryPolicy — bounded attempts, backoff, idempotent-only
  dio_api_client.dart        DioApiClient — the only file that imports dio
  fake_api_client.dart       FakeApiClient — deterministic test double
  request_id_factory.dart    RequestIdFactory — correlation ids

lib/core/secure_storage/     (module: secure-storage)
  secure_store.dart          SecureStore interface
  flutter_secure_store.dart  FlutterSecureStore — the only file that imports the plugin
  in_memory_secure_store.dart InMemorySecureStore — test double

lib/core/diagnostics/        (module: diagnostics)
  error_reporter.dart        ErrorReporter interface
  local_error_reporter.dart  LocalErrorReporter — in-memory, never networked
  app_error.dart             AppError — severity, message, cause, context
```

Rules that follow from the road map and the protocol:

- Only `dio_api_client.dart` imports `dio`; only `flutter_secure_store.dart` imports
  `flutter_secure_storage`. Every other file in a module is transport-agnostic.
- Features never see a `DioException` or a `FlutterSecureStorage` type. They see `ApiResult<T>`,
  `ApiError`, and `SecureStore`.
- No `print` anywhere; the `AppLogger` is the only sink.

### 6.2 Composition root

`architecture-core` gains no optional types. Instead the brick generates
`lib/app/app_services.dart` when at least one service module is selected:

```dart
class AppServices {
  const AppServices({required this.logger, required this.apiClient, ...});
  final AppLogger logger;      // present when logging is selected
  final ApiClient apiClient;   // present when networking is selected
  final SecureStore secureStore;
  final ErrorReporter errorReporter;
}

AppServices buildAppServices(AppConfig config) { ... }
```

Only the selected fields exist, so the file is absent from a blank project. `bootstrap.dart` gains a
conditional import and passes `services` to `DevFluttApp`; `DevFluttApp` gains a conditional
`AppServices` field. `DevFluttApp` loses its `const` constructor in every variant (a service graph
is never const) — a public-contract change, recorded in `CHANGELOG.md`.

Riverpod is **not** required by any new module. `state-riverpod` remains orthogonal; the services
are passed by constructor injection.

### 6.3 Retry and idempotency policy (ADR-004)

- Retry is opt-in per request through a typed `RetryPolicy`; the default policy retries **nothing**.
- Only `GET`, `HEAD`, and `OPTIONS` are retried. `POST`, `PUT`, `PATCH`, and `DELETE` are never
  retried automatically, because the template cannot know whether the backend has an idempotency key.
- Bounded: at most 3 attempts, exponential backoff with a 30 s ceiling, total elapsed budget of
  60 s. Exhaustion produces a typed `ApiError.timeout` (or the last mapped error), never an
  unhandled exception.
- Retried requests carry the same `X-Request-Id` so a backend can correlate the attempts.

### 6.4 Error mapping

| Transport condition | `ApiError` |
| --- | --- |
| Connect/socket failure | `ApiError.network` |
| `connectTimeout` / `receiveTimeout` / `sendTimeout` | `ApiError.timeout` |
| `cancelToken.isCancel` | `ApiError.cancelled` |
| HTTP 4xx / 5xx | `ApiError.http(status, body)` |
| Body that is not the expected shape | `ApiError.malformed` |
| Anything else | `ApiError.unknown` |

The original message and status are preserved, but the raw body is **not** included in
`ApiError.http` — the body may contain personal data. The body is available to the caller only
through a separate, explicitly requested accessor.

### 6.5 Redaction policy

The `Redactor` replaces values with `<redacted>` when:

- the field key matches (case-insensitive): `authorization`, `proxy-authorization`, `cookie`,
  `set-cookie`, `password`, `passwd`, `secret`, `token`, `access_token`, `refresh_token`,
  `id_token`, `api_key`, `apikey`, `client_secret`, `private_key`, `session`, `credit_card`,
  `card_number`, `cvv`, `cvc`, `pin`;
- the value itself matches a token-like pattern (a JWT, a long opaque bearer value, a
  `Basic <base64>` header);
- the value is under a key whose name contains `authorization` or `credential`.

Redaction is applied **before** a record reaches any sink, so a sink cannot leak by omission.
The redaction corpus is a committed fixture so a regression is a failing test, not a silent
behaviour change.

### 6.6 Android platform requirements for `secure-storage`

- Minimum Android API 23 (the plugin's floor). The template's `minSdk` is 24, so no change is
  needed today; the requirement is still documented.
- Android auto-backup would restore the plugin's encrypted SharedPreferences without the Keystore
  key, producing `InvalidKeyException: Failed to unwrap key`. The brick therefore generates, when
  the module is selected:
  - `android/app/src/main/res/xml/backup_rules.xml` excluding the `FlutterSecureStorage` shared
    preference file;
  - `android/app/src/main/res/xml/data_extraction_rules.xml` doing the same for Android 12+;
  - `android:fullBackupContent` and `android:dataExtractionRules` attributes on `<application>`.

  Excluding the plugin's file is preferred over `android:allowBackup="false"`, which would disable
  backup for the whole application.
- No new Android **permission** is introduced. `USE_BIOMETRIC` is *not* added, because biometric
  storage is an opt-in configuration the developer may never use; the module README documents how
  to enable it and what it requires (API 28+ for enforced biometrics).

### 6.7 CI supply-chain gates

Two new jobs, both using pinned binaries with published-checksum verification, no third-party
actions:

- **secret-scan** — `gitleaks` pinned version, SHA-256 verified against the release's published
  `checksums.txt`, run over the full history with `--redact`.
- **dependency-audit** — `osv-scanner` pinned version, SHA-256 verified, scanning
  `pubspec.lock` and `tool/ftemplate_cli/pubspec.lock`.

Plus a `license-inventory` job that regenerates `THIRD-PARTY-NOTICES.md` and fails when the
committed file differs.

### 6.8 Generator and manifest impact

- No manifest **schema** change: the new fields are expressible with the existing vocabulary
  (`pubDependencies`, `nativeChanges.android`, `requiredSetup`, `configKeys`, `privacy`,
  `outputs`, `tests`). This avoids a schema-contract change in a 0.x release.
- New brick variables: `hasLogging`, `hasNetworking`, `hasSecureStorage`, `hasDiagnostics`.
- The generator maps module IDs to those variables, exactly as v0.3.0 does for the existing six
  modules.
- `API_BASE_URL` is already a configuration key of `architecture-core`; the `networking` module
  consumes it and declares no new key.
- The new modules' `pubDependencies` flow through the existing `extraDependencies` mechanism, so
  `dio` and `flutter_secure_storage` land in the generated `pubspec.yaml` automatically.

**V2 (milestone gate).** Root format/analyze/test; generator format/analyze/test; manifest
validation; **static matrix** over every preset and the four new modules in isolation and in
combination; **built matrix** for `blank`, `core`, `demo`, and `recommended`; debug and release
Android builds of the reference app and of the `recommended` output; merged-release-manifest
permission review for `blank` and `recommended`; secret scan; dependency audit; licence-inventory
check; generation determinism; dry-run-versus-output comparison; documentation checks.

**V3 (release gate).** Everything in V2 for the full matrix on the exact candidate commit, from a
clean checkout, in CI; the reference app's debug and release builds; the release APK permission
review; the tag→commit identity check; the remote release verification.

**Static matrix (cheap, every manifest/brick change).** Enumerate every selection the validator
accepts and every selection it must reject, and for each: the accept/reject decision and the
message; the file list versus the dry-run; `pubspec.yaml` dependencies versus the manifests; the
imports, routes, registrations, permissions, and configuration keys versus the selection; and the
absence of residue from unselected modules. The enumeration is computed from the manifests, not
hand-written, so a new module cannot silently escape the matrix.

**Built matrix (expensive, scoped at V2, complete at V3).** `blank`, `core`, `demo`,
`recommended`; each new module in isolation with only its declared prerequisites; the documented
pairwise set (`logging`×`networking`, `networking`×`secure-storage`, `networking`×`diagnostics`,
`secure-storage`×`diagnostics`, `logging`×`diagnostics`); and the maximum-capability composition
(`recommended`).

**Coverage method and gaps.** The static matrix is exhaustive over the manifest space; the built
matrix is exhaustive over the four presets, the four new modules in isolation, and the documented
pairwise set. It is **not** exhaustive over all module combinations, and the report will say so
explicitly. iOS is **unverified** — no macOS host or runner exists.

## 12. Security, privacy, accessibility, localization notes

**Security.** The milestone's centre of gravity. Concretely: redaction by default and before the
sink; `ApiError.http` excludes the response body; a `SecureStore` interface instead of direct
plugin access; no token in the client configuration (the base URL is not a secret); the generated
Android build adds no permission; the backup exclusion prevents restoring ciphertext without the
Keystore key; CI blocks committed secrets and known-vulnerable dependencies.
`docs/SECURITY-BASELINE.md` records the threat-model boundary and maps the relevant OWASP MASVS
items to the validation steps, without claiming MASVS compliance.

**Privacy.** Blank and core make no network call. `networking` is the only module that can produce
outbound traffic, it is opt-in, and its manifest declares `privacy.network: true`.
`diagnostics` declares `privacy.telemetry: false` and the local adapter never transmits. No
analytics module ships in this milestone.

**Accessibility.** The new modules add no widgets, so the accessibility surface is unchanged. The
one UI-visible change is the root widget's constructor losing `const`, which has no accessibility
consequence. `docs/ARCHITECTURE.md` will note that the new modules add no user-facing text, hence
no localization surface, and that localization remains a v0.8.0 concern.

**Localization.** No user-facing strings are introduced.

## 13. Dependency / license / security impact

| Dependency | Version | Licence | Why | Transitive | Fallback |

`docs/TESTING.md`.

**Licence inventory.** `THIRD-PARTY-NOTICES.md` is generated from the two lockfiles and lists each
package with its licence, version, and upstream URL, plus the notices the licences require.

## 15. Risks and mitigations; rollback/recovery

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| The Android backup-exclusion resources are wrong, so a restored build throws `InvalidKeyException` | Medium | High (runtime failure on restore) | Exclusion by exact path, verified against the plugin's own README; merged-manifest inspection; a debug build of the module; documented in the module README |
| The redaction corpus is too narrow and a secret shape slips through | Medium | High | Redaction is applied before the sink, so a missing pattern still cannot leak a *known* key name; the corpus covers the MASVS-relevant shapes; the corpus is a committed fixture so it grows deliberately |
| The retry policy replays a non-idempotent request | Low | High (duplicate orders) | The policy allows only `GET`/`HEAD`/`OPTIONS` by default; a unit test asserts a `POST` is attempted exactly once |
| `dio` is a heavy abstraction and the template over-uses it | Medium | Medium | Exactly one file imports `dio`; the rest of the module is transport-agnostic; a lint-style generator test can assert the import count |
| The brick's conditional combinatorics grow (`hasGoRouter` × service flags) | Medium | Medium | The service flags collapse into one `hasServices` flag for the composition file; `DevFluttApp` loses `const` so there is one constructor; the formatter normalises the layout |
| A dependency advisory appears between planning and the release gate | Medium | Medium | OSV-Scanner runs in CI on every push; the report records the scan date and the versions scanned; the freshness re-check happens at V3 |
| gitleaks or OSV-Scanner cannot be downloaded in the CI runner | Low | Medium | Both are downloaded from GitHub releases with checksum verification; the failure mode is a red job, never a false green |
| Adding `logging` to the `core` preset breaks existing users' expectations | Low | Low | `logging` adds no dependency; the change is recorded in `CHANGELOG.md` and `docs/UPGRADING.md` |

**Rollback.** Each slice is one commit on `work/v0.4.0`; a bad slice is reverted with
`git revert` on the branch. The release is a pre-release tag, so a failed V3 gate produces a new
commit and a full re-run — never a retag. If the `recommended` preset proves unstable, it can be
withdrawn from the preset set in a follow-up commit without affecting the four modules.
