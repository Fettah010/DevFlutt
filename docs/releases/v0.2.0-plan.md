## 1. Outcome and success definition

A validated generation pipeline that produces `blank` and `core` Flutter projects from a CLI, with a
versioned module-manifest schema, a dependency/conflict graph with actionable diagnostics, and
deterministic, safe output. Generated projects are independent of the generator at runtime.

## 6. Design / architecture

```text
tool/ftemplate_cli/
  bin/ftemplate.dart                 # entry point
  lib/ftemplate_cli.dart
  lib/src/
    cli.dart                         # arg parsing + dispatch
    models/                          # ProjectSpec, ModuleSelection, GenerationResult
    manifest/                        # loader + validator
    presets/                         # preset definitions
    graph/                           # dependency/conflict resolution + diagnostics
    generator/                       # Mason-based generation engine
    metadata/                        # template metadata writer
  test/
bricks/
  project/                           # base scaffold (pubspec, lib/, android/, test/)
  modules/state_riverpod/            # lib/core/state/...
  modules/navigation/                # lib/app/app_router.dart, routes
manifests/
  schema/module.schema.json         # contract
  modules/*.yaml                    # one per module
  presets/*.yaml                    # blank, core
```

**Composition model.** The generator validates the selection, computes the union of
dependencies/permissions/config keys, runs the `project` brick with those values as vars, then runs
each selected module brick. No regex rewriting of Dart/Gradle/manifest files.

**Determinism.** Same inputs + same template version → identical output. No timestamps in generated
source. Verified by generating twice and diffing.

**Safety.** Generate into a temp dir, validate, then move. Refuse to overwrite a non-empty
destination unless `--force`.

## 8. Acceptance criteria

| AC-01 | CLI tests cover valid, invalid, missing, duplicate, conflicting, unsupported options | CI test run | V2 |
