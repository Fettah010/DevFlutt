## 1. Outcome and success definition

A developer can add authentication to a generated project by choosing a provider, without the
app's feature-facing contracts changing when the provider changes. Three providers ship
independently selectable: a custom REST/JWT backend, Firebase Auth, and Supabase Auth. All
three satisfy one provider-neutral contract, verified by one shared contract-test suite.

Success is concrete:

- Selecting `--auth rest`, `--auth firebase`, or `--auth supabase` produces a project that
  compiles, analyzes, and passes its tests, with exactly one provider SDK present and only
  the SDKs the selection implies.
- `--auth none`, and every preset that does not name a provider, produce a project with no
  auth SDK, no auth dependency, and no auth configuration file.
- A request for a capability the chosen provider lacks fails at generation time with an
  actionable message naming the provider, the capability, and the providers that have it.
- Two concurrent expired-token requests trigger exactly one token refresh, and a failed
  refresh signs the user out instead of retrying forever.

## 3. Research

Format: Question → Options → Evidence (date) → Finding → Impact → Decision → Validation.

### Q1 — What shape should the provider-neutral auth contract take?

- Options: (a) one interface plus typed errors; (b) a `Result`-style free-function API;
  (c) expose provider SDK types directly.
- Evidence: roadmap §6.2 "provide a provider-neutral auth contract"; §5.4 "Use a predictable
  result/error contract … avoid a maze of wrapper abstractions"; protocol §8.2 "Provider SDK
  types stay behind adapters". The v0.4.0 `ApiClient` / `ApiError` / `ApiResult` trio (shipped
  and tested) is the established in-repo convention.
- Finding: (c) violates the roadmap and would make the contract change with the provider —
  the exact outcome this milestone exists to prevent. (b) has no place to hang the session
  lifecycle, the capability descriptor, or the auth-state stream. (a) matches the repo.
- Decision: an `AuthAdapter` interface, an immutable `AuthSession`/`AuthUser`, a sealed
  `AuthError`, an `AuthState` value with a status enum, and an `AuthCapabilities` descriptor.
  The pattern mirrors v0.4.0's networking layer exactly.
- Validation: the shared contract-test suite runs unchanged against all three adapters.

### Q2 — Which adapters ship in v0.5.0?

- Options: (a) all three named by the roadmap; (b) `auth-rest` only; (c) `auth-rest` +
  `auth-firebase`.
- Evidence: roadmap `v0.5.0` Implement — "Add the custom REST/JWT adapter. Add Firebase Auth
  and Supabase Auth adapters as independently selected modules after verifying current APIs,
  native setup, licenses, and maintenance." The exit criteria say "Each adapter passes
  contract tests", which is plural.
- Finding: (b) and (c) would leave the milestone's own exit criteria unmet.
- Decision: all three, as three independently selected modules with a shared contract.
- Validation: three adapters, three contract-test invocations, three built-matrix entries.

### Q3 — What are the current provider package facts?

Checked on **2026-10-22** against pub.dev and the installed packages in the pub cache.

| Package | Version | License | Publisher | SDK constraint | Transitive (direct) | Maintenance signal |
|---|---|---|---|---|---|---|
| `firebase_auth` | **7.0.0** | BSD-3-Clause | firebase.google.com | Dart ^3.6.0, Flutter >=3.16.0 | `firebase_auth_platform_interface` 9.1.1, `firebase_auth_web`, `firebase_core` 5.0.0, `meta` | 1.93M downloads, 4.3k likes, published 6 days before the check |
| `firebase_core` | **5.0.0** | BSD-3-Clause | firebase.google.com | Dart ^3.6.0, Flutter >=3.27.0 | `firebase_core_platform_interface` 8.1.1, `firebase_core_web`, `meta` | 5.38M downloads, published 7 days before the check |
| `supabase_flutter` | **2.18.3** | MIT | supabase.io | Dart >=3.9.0 <4.0.0, Flutter >=3.35.0 | `app_links` 7.2.2, `shared_preferences` 2.5.6, `url_launcher` 6.3.3, `supabase` 2.16.5, `supabase_common`, `logging`, `async`, `meta` | 1.32M downloads, 983 likes, published 10 days before the check |

- Evidence: pub.dev package pages and the pub.dev API on 2026-10-22; the package sources in
  the local pub cache; the `firebase_auth` 7.0.0 changelog; the FlutterFire "Get started with
  Firebase in your Flutter project" documentation (page last updated 2026-10-22).
- Findings that changed a decision:
  1. `firebase_auth` 7.0.0 **requires minSdk 24** (it moved to Firebase BoM 35). The
     template's `flutter.minSdkVersion` is exactly 24, so the requirement is met with no
     margin — and any future bump of the template's minSdk floor is not needed for Firebase.
     Verified in the Flutter SDK's `FlutterExtension.kt`.
  2. `firebase_auth` 7.0.0 and `firebase_core` 5.0.0 **apply the Kotlin Gradle Plugin**.
     Flutter 3.47 emits the warning "Future versions of Flutter will fail to build if your
     app uses plugins that apply KGP". The build succeeds today; the deprecation path is
     real and must be documented, not hidden.
  3. `supabase_flutter` 3.0.0-dev.12 is a **pre-release** and is rejected by the protocol's
     dependency policy.
  4. `supabase_flutter` persists the session with `SharedPreferencesLocalStorage` by
     default — the session, which carries the access **and refresh tokens**, lands in an
     unencrypted preferences file that Android Auto Backup includes by default. The package
     documents a `LocalStorage` interface so a `flutter_secure_storage` implementation can
     be supplied, selected through `FlutterAuthClientOptions(localStorage:)`.
  5. The FlutterFire path needs **no `google-services.json` and no
     `com.google.gms.google-services` Gradle plugin**. `flutterfire configure` writes
     `lib/firebase_options.dart`, and the official documentation states that the config file
     "contains unique, but non-secret identifiers". The native Android SDK's
     `google-services` path is not the Flutter path.
- Decision: pin `firebase_core: ^5.0.0` and `firebase_auth: ^7.0.0` for `auth-firebase`;
  pin `supabase_flutter: ^2.18.3` for `auth-supabase`; reject the Supabase pre-release; make
  `auth-supabase` depend on `secure-storage` and supply a secure `LocalStorage` rather than
  the package default; ship an inert `firebase_options.dart` placeholder that the developer
  replaces with `flutterfire configure`; document the KGP deprecation warning.
- Validation: **proof-of-concept builds**. A throwaway app with `firebase_core` +
  `firebase_auth` built a debug APK (140.9 s) on the template's toolchain; a throwaway app
  with `supabase_flutter` built a debug APK (102.5 s) on the same toolchain. The generated
  `auth-firebase` and `auth-supabase` presets are rebuilt in the built matrix.

### Q4 — How is token refresh kept concurrency-safe?

- Options: (a) a single-flight coordinator in `auth-core`, reused by every adapter that
  refreshes itself; (b) per-adapter locking; (c) rely on the provider SDK.
- Evidence: roadmap §5.4 "Token refresh must be concurrency-safe: concurrent expired-token
  requests should not start many refresh requests or retry in a loop. Define logout behavior
  when refresh fails."; `v0.5.0` exit criterion "Concurrent token-expiry tests prove refresh
  is serialized and does not loop indefinitely."
- Finding: (c) is true for Firebase and Supabase, whose SDKs own refresh, but `auth-rest`
  talks to an arbitrary backend and must implement refresh itself — and it must do so
  correctly on the first try, because the provider SDKs' behaviour cannot be the template's
  contract.
- Decision: `auth-core` ships a `TokenRefreshCoordinator` that collapses concurrent
  refreshes onto one in-flight future. A failed refresh rejects the waiters **and** signs the
  user out; the coordinator never re-arms itself, so it cannot loop.
- Validation: a concurrency test fires N simultaneous refresh requests against a slow fake and
  asserts exactly one refresh call, plus a test that a failing refresh signs out and does not
  retry.

### Q5 — How should the generator represent "auth" versus "backend"?

- Options: (a) one overloaded `--backend` flag; (b) a separate `--auth` flag now, with
  `--backend` reserved for the data-backend adapters; (c) module selection only.
- Evidence: roadmap §6.3 "Backend selection is not always identical to auth selection: for
  example, an app can consume a custom REST API while using a third-party identity provider.
  The generator must represent these decisions clearly instead of using one overloaded
  `backend` flag."; §4.3 lists `--backend` as a *proposal*.
- Finding: `--backend` has **never shipped** — the v0.4.0 CLI has no such flag — so adding
  `--auth` is new surface, not a break. The `v0.5.0` Implement list contains no data-backend
  adapter (Firestore, Postgres, Storage); adding a `--backend` flag with nothing behind it
  would be a hollow contract.
- Decision: v0.5.0 adds `--auth none|rest|firebase|supabase` as an **explicit identity
  decision**, separate from any future `--backend`. The two decisions are recorded as
  separate in ADR-006 so the data-backend milestone adds `--backend` without overloading
  `--auth`. The underlying selection is still modules, so `--module auth-firebase` remains
  valid and composes with `--auth`.
- Validation: `--auth` and `--module` are tested independently and together in the CLI tests.

### Q6 — How are provider capabilities communicated, and how does the generator fail?

- Options: (a) capabilities only at runtime; (b) capabilities in the module manifest plus a
  `--auth-capability` requirement the generator validates; (c) one module per capability.
- Evidence: roadmap §6.2 "Do not assume all providers support the same operations. The
  generator should communicate missing capabilities, not pretend every adapter is identical.";
  `v0.5.0` Implement "Add backend capability descriptors and explicit generator errors where
  providers differ."
- Finding: the providers genuinely differ. `auth-rest` supports email/password, optional
  registration, password reset, session restoration, refresh, and logout. Firebase and
  Supabase additionally support **one-time-password (email link / magic link) sign-in**,
  phone sign-in, anonymous sign-in, and MFA. Social sign-in is **not shipped in this
  milestone** for any adapter (it needs provider-console setup and platform configuration
  that cannot be exercised or verified here).
- Decision: (b). The manifest gains an optional `capabilities` list; the CLI gains
  `--auth-capability` (repeatable) declaring what the app needs; the generator refuses a
  selection whose adapter cannot provide a declared capability, naming the adapter, the
  capability, and the adapters that do provide it. At runtime the same information is on
  `AuthAdapter.capabilities`, and an unsupported call throws a typed
  `AuthError.unsupportedCapability` rather than failing obscurely.
- Validation: generator tests for the accepted and rejected selections, and a contract test
  asserting that an unsupported call yields the typed error.

### Q7 — What native setup does each provider need on Android?

- Options: (a) generate native configuration files; (b) ship placeholders and document the
  provider's own tooling.
- Evidence: the FlutterFire documentation (2026-10-22) states the Android requirement is
  API 24 or higher, and that `flutterfire configure` creates the Firebase app registrations
  and writes `lib/firebase_options.dart`. The Supabase documentation requires a project URL
  and a publishable key at `Supabase.initialize`, and deep links for magic link, password
  reset, and OAuth.
- Finding: (a) would mean committing a `google-services.json`-shaped file that the provider
  tooling then overwrites, and would require a redirect allow-list the template cannot know.
  Deep links additionally need a per-project scheme that only the developer can choose.
- Decision: (b). The template ships **inert placeholders** — `lib/firebase_options.dart` for
  Firebase and a configuration file for Supabase — whose values are unmistakably fake. The
  generated code detects an unconfigured placeholder and **fails fast with an actionable
  message** naming the exact command to run. Provider-side setup is documented per adapter.
- Validation: a generated `auth-firebase` and `auth-supabase` project start with the
  placeholder in place and surface the configuration error rather than failing obscurely.

### Q8 — Does the milestone include auth UI?

- Options: (a) a login screen and auth form states; (b) infrastructure only.
- Evidence: roadmap `v0.8.0` — "polished UI states", "Complete core UI components: form
  fields, buttons, messages, empty/error/loading/offline states"; `v0.9.0` — "Add
  integration-test flows for authentication, deep links". The `v0.5.0` Implement list contains
  no UI bullet, but §6.2 does require auth forms to have validation, busy, success, failure,
  offline, and recovery states.
- Finding: the form and its state handling belong to the milestone that owns "polished UI
  states"; the v0.5.0 list requires "router integration", which is the redirect behaviour,
  not the screen.
- Decision: (b). v0.5.0 delivers the contract, the adapters, the session model, the refresh
  coordinator, the capability descriptor, and the **router redirect helper** — a pure
  function that returns the login location for an unauthenticated user and preserves the
  requested destination. The login screen and its form states are deferred to v0.8.0, and the
  deferral is recorded in `docs/DEFERRED.md`.
- Validation: the redirect helper is unit-tested for the unauthenticated, authenticated, and
  offline cases, and the deep-link destination preservation is tested.

## 4. In scope

- A provider-neutral auth contract, auth-state model, capability descriptor, session store
  interface, secure session store, single-flight token-refresh coordinator, and a
  provider-neutral router-redirect helper.
- Three adapters as independently selected modules: `auth-rest`, `auth-firebase`,
  `auth-supabase`, each behind a provider-port interface with a real implementation and a
  fake, exactly as the v0.4.0 networking layer is structured.
- One shared contract-test suite, run against every adapter, covering only the capabilities
  that adapter implements.
- Generator support: the `auth-core` plus three adapter manifests, mutual conflicts between
  the adapters, an optional `capabilities` manifest field, the `--auth` and
  `--auth-capability` CLI options, an explicit generator error for an unsatisfiable
  capability, and the adapter capabilities printed in the generation summary.
- Inert provider configuration placeholders, per-provider setup documentation, and a
  fail-fast configuration check.
- The defect found in P0 in the verify script's `aapt2` resolution.

## 5. Out of scope

- **Auth UI** — login screen, sign-up form, form validation, busy/success/failure/offline
  states. Belongs to v0.8.0 ("polished UI states"). Deferred to `docs/DEFERRED.md`.
- **Social sign-in** — Google, Apple, Facebook. Each needs provider-console setup and
  platform configuration that cannot be exercised here, and the roadmap makes social
  sign-in an opt-in subfeature. The capability descriptor reports it unsupported for every
  adapter in this release.
- **Data backends** — Firestore, Postgres, Storage, Realtime, Edge Functions. The `v0.5.0`
  Implement list does not contain them, and the roadmap's §6.3 point is that backend
  selection is a **separate** decision from auth selection. `--backend` is therefore not
  introduced in this release; ADR-006 reserves the name.
- **Multi-factor authentication**, phone sign-in, and anonymous sign-in. Supported by the
  Firebase and Supabase SDKs but not by the provider-neutral contract in this release.
- **Live provider verification** — no Firebase project, Supabase project, credentials, or
  redirect allow-list is available. Recorded as OA-6 and OA-7. All provider behaviour in this
  release is **Contract-tested** against fakes, never claimed as live-verified.
- **iOS** — no macOS host or runner. The Dart layer is platform-independent; the native
  configuration is Android-only and the iOS claim stays **unverified**, as in v0.4.0.
- **Backend selection flag** — `--backend` (see §3 Q5).
- **Caching, offline queueing, and token storage policy beyond the session** — ADR-004
  defers the response cache to v0.6.0.

## 6. Design / architecture

### 6.1 Module graph

```text
architecture-core, logging, secure-storage
        │
     auth-core ──────────────┬──────────────┐
        │                    │              │
   (requires)          auth-rest      auth-firebase   auth-supabase
   networking          (requires:     (requires:      (requires:
                       auth-core)     auth-core)      auth-core)
```

- `auth-core` — the provider-neutral layer. Requires `architecture-core`, `logging`, and
  `secure-storage`: the session store is part of the contract, so it needs the secure store
  and the Android backup rules that keep the session out of backups. (Plan amendment,
  2026-10-22: `secure-storage` moved from the adapters to `auth-core` so that one session
  store serves every adapter, and so that no adapter can be selected without it.)
- `auth-rest`, `auth-firebase`, `auth-supabase` — mutually conflicting
  (`conflictsWith` each other), so the existing compatibility graph rejects a selection of
  two providers with an actionable message and no schema change is needed.
- `auth-rest` additionally requires `networking`, because it talks to a backend through the
  template's `ApiClient`. The other two need no other module.

### 6.2 The contract (`auth-core`)

| File | Contents |
|---|---|
| `lib/core/auth/auth_capabilities.dart` | `AuthCapability` enum, `AuthCapabilities` immutable set, `supports()` |
| `lib/core/auth/auth_error.dart` | sealed `AuthError`: `invalidCredentials`, `network`, `timeout`, `cancelled`, `sessionExpired`, `sessionRevoked`, `notSignedIn`, `unsupportedCapability`, `providerFailure`, `unknown` |
| `lib/core/auth/auth_session.dart` | `AuthUser`, `AuthSession` (access token, refresh token, expiry, user) |
| `lib/core/auth/auth_state.dart` | `AuthStatus` enum, `AuthState` value |
| `lib/core/auth/auth_adapter.dart` | the `AuthAdapter` interface |
| `lib/core/auth/session_store.dart` | `SessionStore` interface (read / write / clear) |
| `lib/core/auth/secure_session_store.dart` | `SecureSessionStore` over the `SecureStore` of the `secure-storage` module |
| `lib/core/auth/token_refresh_coordinator.dart` | the single-flight refresh coordinator |
| `lib/core/auth/auth_route_redirect.dart` | the provider-neutral router-redirect helper |
| `lib/core/auth/auth_controller.dart` | the app-facing controller: current state, state stream, delegating operations |

`AuthAdapter` surface: `capabilities`, `currentState`, `authStateChanges`,
`restoreSession()`, `signInWithEmailAndPassword`, `registerWithEmailAndPassword`,
`requestPasswordReset`, `signOut`, and `refreshSession`.

The `AuthAdapter` is deliberately **not** a Riverpod type. `auth-core` must not depend on the
state-management module; the app wraps `AuthController` in its own provider, and the module
documentation shows the three lines that do it.

### 6.3 The adapters

Each adapter module has the same four-layer shape, so a feature never sees an SDK type:

| Layer | Purpose |
|---|---|
| `*_auth_port.dart` | the provider boundary — the only interface the adapter depends on |
| `*_auth_adapter.dart` | the provider-neutral logic over the port |
| `*_auth_port_impl.dart` | the real implementation over the provider SDK |
| `fake_*_auth_port.dart` | the fake used by the contract suite |

- `auth-rest` — `RestAuthConfig` declares the endpoint paths and the payload shapes
  (login, register, refresh, logout, password reset) and the token field names. Nothing is
  hard-coded to one backend; the adapter maps the app's request/response shapes onto the
  configured paths. The real port uses the `ApiClient` of the `networking` module, so the
  existing timeout, cancellation, correlation, and redaction behaviour applies to auth
  traffic too.
- `auth-firebase` — the real port wraps `firebase_auth`. The module ships an inert
  `lib/firebase_options.dart`; the developer replaces it with `flutterfire configure`. The
  generated composition root fails fast, with the command to run, when the placeholder is
  still in place.
- `auth-supabase` — the real port wraps `supabase_flutter`. The session is persisted through
  a `LocalStorage` implementation backed by the template's `SecureStore`, **not** the
  package's `shared_preferences` default, so the refresh token is not written to an
  unencrypted, auto-backed-up file. The module ships inert URL and publishable-key
  placeholders.

### 6.4 Refresh serialization

`TokenRefreshCoordinator` holds at most one in-flight refresh future. The first caller
starts the refresh; every later caller awaits the same future. The future completes with the
new session, or fails — in which case the coordinator calls the adapter's sign-out exactly
once and rejects all waiters. There is no timer, no retry, and no re-arm, so it cannot
loop. `auth-rest` uses the coordinator; Firebase and Supabase refresh inside their SDKs and
are not wrapped by it, which is recorded in the adapter documentation.

### 6.5 Router integration

`authRouteRedirect` is a pure function: given the current `AuthState`, the requested
location, and the login location, it returns the location to navigate to, or `null` to allow
the navigation. For an unauthenticated user it returns the login location with the intended
destination preserved in a query parameter, so a protected deep link returns the user to
where they were going after signing in. The generator adds a `hasAuthRouter` boolean
variable, and the `navigation` module's `route_guard.dart` wires the helper when both
`auth-core` and `navigation` are selected.

### 6.6 Generator surface

- `--auth none|rest|firebase|supabase` — adds the matching adapter module (`none` adds
  nothing). Default `none`.
- `--auth-capability <id>` — repeatable. Declares a capability the app needs. The generator
  resolves it against the selected adapter's manifest-declared capabilities and **fails** with
  an actionable message when it is not available. Valid capability ids are printed by
  `ftemplate list-modules` and by the error message itself.
- The manifest schema gains an optional `capabilities` array. The `create` summary prints the
  selected adapter and its capabilities.

### 6.7 ADR-006

`docs/adr/ADR-006-auth-and-backend-adapters.md` records: the contract shape, the three
adapters and their capability differences, the auth-versus-backend split and the reserved
`--backend` name, the refresh-serialization design, the secure-persistence decision for
Supabase, and the placeholder-configuration policy.

## 10. Change-impact → gate selection; matrix definition and coverage method

**Per-slice (V1).** `dart format` and `flutter analyze` on the touched package; the focused
tests for the touched paths; manifest validation and the static matrix for any manifest,
brick, or generator change; the CLI tests for any generator change; the shared contract suite
for any adapter change; the concurrency test for any refresh change; the secret scan for any
change that touches configuration handling.

**V2 milestone gate.** Full format / analyze / unit / widget / CLI tests for the reference app
and the generator; manifest validation for every manifest; the static matrix over the
admissible selections; the built matrix for `blank`, `core`, `demo`, `recommended`, and the
three auth presets; a release build for the reference app and for `auth-firebase` and
`auth-supabase`; merged-manifest permission review; the secret scan; the dependency audit;
the licence inventory; the generation determinism check; the documentation and link checks;
and the gate self-test for the changed CI and verify behaviour.

**V3 release gate.** The full V2 set on the exact candidate commit, from a clean CI checkout,
plus the freshness re-check of every package version and advisory (§6.2 requires a
re-verification for facts older than 14 days; the provider package facts in §3 Q3 were checked
on 2026-10-22 and are inside the window at the release gate), the tag-readiness checks, and
the size comparison against the v0.4.0 baseline.

**Matrix coverage method.** The static matrix enumerates every selection the validator
accepts and every selection it must reject, and checks the file list, the dependencies, the
imports, the permissions, the configuration keys, and the absence of residue. The built
matrix covers the four presets and the three auth presets. The pairwise set over compatible
modules is **not** exhaustive in this milestone: the combinations of two auth modules are
rejected by design, and the combinations of an auth module with each other module are
covered by the three auth presets only. `docs/COMPATIBILITY.md` records the method and the
gap. The maximum-capability composition and the exhaustive pairwise set remain v0.9.0 work.

  grows. The measurement is reported per preset; no "lightweight" claim is made.

## 12. Security, privacy, accessibility, localization notes

- Access tokens, refresh tokens, and session secrets live in the `secure-storage` module's
  `SecureStore` for `auth-rest`; the Supabase session is persisted through a
  secure-storage-backed `LocalStorage`; the Firebase SDK manages its own persistence.
- The redaction corpus in the `logging` module is extended with auth-shaped values — a
  bearer token, a refresh token, a password, an `Authorization` header — and the
  `auth-rest` traffic passes through the same redactor, so an auth request cannot log a
  credential.
- Logout clears the local session and the persisted session, per the documented policy.
- Server-side responsibilities — authorization, rate limiting, MFA policy, revocation, and
  account recovery — are documented as backend duties and are never implied by the client.
- Accessibility and localization: this milestone adds no user-facing UI, so it adds no
  semantics, RTL, or text-scaling surface. The redirect helper preserves the deep-link
  destination as a URL-encoded value, which is direction-neutral.

## 15. Risks and mitigations; rollback and recovery

| ID | Risk | Tier | Mitigation | Recovery |
|---|---|---|---|---|
| R1 | The provider SDKs are fresh majors (`firebase_auth` 7.0.0, `firebase_core` 5.0.0, `supabase_flutter` 2.18.3) and their Dart API may differ from what this plan assumes | R3 | The adapter logic depends on a **port interface**, not on the SDK, so an SDK change touches one thin file. The proof-of-concept builds already succeeded against these exact versions | Re-pin to the previous minor, or adjust the port implementation |
| R2 | `firebase_auth` and `firebase_core` apply the Kotlin Gradle Plugin, and Flutter 3.47 warns that future Flutter versions will fail to build such plugins | R3 | The warning is documented in the module document and in `docs/COMPATIBILITY.md`; the build succeeds on the pinned toolchain | Pin a Flutter version without the KGP check, or wait for the plugin migration |
| R3 | The provider SDKs add native code and may need an Android SDK or Gradle floor the template does not have | R3 | Both proof-of-concept builds succeeded on the template's exact toolchain, compileSdk 36, minSdk 24 | Raise the module's declared platform floor and record it |
| R4 | Session handling is the highest-risk area in the template (roadmap §4.3 R3) | R3 | Red-first tests, an explicit edge-case list, the shared contract suite, and a second review pass of the diff before the merge | Revert the module; the rest of the milestone is independent |
| R5 | The verify script's `aapt2` resolution omits `.exe`, so the release-permission check **always skips on Windows** — the check has never actually run locally | R2 | Found in P0 and fixed in T16; the check is then proven to run, and the gate self-test is re-run | Revert T16 alone; it is independent of the auth work |
| R6 | A generated `auth-firebase` project cannot start without a real Firebase project, so the built matrix cannot exercise the live flow | R3 | The provider is behind a port; the contract suite runs against a fake. The live flow is OA-6, and the claim ledger says **Not claimed** | — |
| R7 | A capability the provider does not have is silently treated as available | R3 | The manifest declares the capabilities; the generator refuses a selection that lacks a declared one; the runtime raises a typed error | — |
| R8 | The scope is large and a half-finished milestone would be worse than a smaller one | R2 | The tasks are in waves; each adapter is independent; the shared contract suite is written before the adapters | Ship `auth-core` + `auth-rest` and defer the other two — a level-C proposal, not an incidental cut |
