## 1. Outcome and success definition

Generated projects can choose non-sensitive preferences, a migrated relational database, an offline-first reference feature, and a small commerce foundation independently. Each choice has an app-owned boundary, predictable state/error handling, tests, and no dependency/native change when unselected.

The v0.7 claim is deliberately bounded: the sample persists local notes and a pending local edit queue, supports explicit refresh and a documented local-wins demonstration policy, and reports whether data is local or refreshed. It does not claim background synchronization, automatic conflict-free merging, or server consistency. Cart totals use demo catalog prices for display only; checkout sends product identifiers and quantities through a contract and accepts the server's authoritative quote/result. No card data is collected or stored.

## 2. Scope and decisions

- Add opt-in `preferences` module using the current Flutter-maintained `SharedPreferencesAsync` API for simple, non-sensitive values only. Secure credentials remain in `secure-storage`.
- Add opt-in `local-database` module using Drift/SQLite, a generated database class and migration strategy, plus injectable in-memory database construction for tests. The initial schema supports the offline sample and optional cart persistence without mixing their repositories.
- Add opt-in `offline-data` reference feature: local and remote repository ports, typed synchronization status, explicit refresh through `ApiClient`, pending edit queue, stable operation IDs, and documented local-wins conflict behavior for the demo. The fake remote supports deterministic online/offline and conflict tests. No worker/background sync.
- Add opt-in `commerce` module: catalog/demo adapter, immutable cart lines, quantity validation and deterministic money arithmetic, empty/loading/error states, checkout request/result/error contract and fake checkout. `commerce-persistence` is an explicit opt-in composition with `local-database`; no payment SDK.
- Keep all new modules out of existing presets. Generate only selected files/dependencies and add Android INTERNET permission only through the existing networking module.
- Update ADR, module/architecture/testing/security/deferred docs, CLI generation tests, changelog, release report, and generated-project CI matrix for affected compositions.

### Research decisions

1. **Preferences API.** Flutter's package documentation identifies `SharedPreferencesAsync` as a persistent simple-value store and the old `SharedPreferences` API as legacy. Use `SharedPreferencesAsync` behind a small typed `PreferencesStore` port; fake it in unit tests. It is not a secrets store.
2. **Relational storage.** Drift provides typed relational queries, schema-versioned migrations, and in-memory database construction for tests; its Flutter companion opens native databases in the app documents directory. Choose Drift/SQLite over hand-written `sqflite` CRUD to keep query/migration behavior typed and isolate SQL in one module. Current stable metadata checked 2026-10-26: `drift` 2.35.3, `drift_flutter` 0.3.1, `drift_dev` 2.35.2, and `build_runner` 2.17.1; Drift packages are MIT and build_runner is BSD-3-Clause. Generated projects receive runtime packages only when the module is selected and `drift_dev`/`build_runner` as dev dependencies so users can regenerate the committed database source. Recheck resolution, license inventory and Android builds before acceptance.
3. **Offline semantics.** Use an explicit local source of truth for reads and a durable pending-operation table for local edits. Network refresh is explicit and idempotent; it never silently overwrites pending local edits. The demo uses local-wins on same-record conflict and exposes that decision in docs/tests. This does not imply general-purpose synchronization.
4. **Checkout boundary.** Client code may calculate a display estimate from demo catalog data, but the checkout request carries item IDs and quantities only. A successful response carries the server quote/order identifier; the local display estimate is never represented as authoritative. No payment SDK or card storage.

Evidence: roadmap §5.4/§11 and protocol dependency/data-safety requirements; [Shared Preferences API](https://pub.dev/documentation/shared_preferences/latest/shared_preferences/SharedPreferencesAsync-class.html), [Drift](https://pub.dev/packages/drift), [Drift Flutter setup](https://pub.dev/packages/drift_flutter), [Drift generator](https://pub.dev/packages/drift_dev), [build_runner](https://pub.dev/packages/build_runner), [Drift migrations](https://drift.simonbinder.eu/migrations/). `shared_preferences` 2.5.6 is Flutter-published/BSD-3-Clause; drift packages are MIT; `build_runner` is BSD-3-Clause. Generated-project dependency resolution and license inventory remain required acceptance evidence.

## 3. Acceptance criteria and claim ledger

| ID | Claim / acceptance criterion | Verification |
|---|---|---|
| AC1 | Preferences store reads/writes/removes supported primitives, with fake-backed tests; generated config excludes credentials from preferences. | Unit tests and generated-file/dependency assertions |
| AC2 | Database initializes at current schema, migrates a previous schema, can reopen without losing committed rows, and has in-memory test support. | Migration tests from prior schema, reopen/data-loss regression tests |
| AC3 | Offline sample distinguishes local reads, pending writes, refresh state and errors; queued operations retain stable IDs and are replayed only by explicit refresh. Safe GET retries follow the existing client policy; unsafe writes are never automatically retried. | Repository contract tests for offline→online, failed explicit refresh, duplicate replay and conflict |
| AC4 | Demo conflict policy is explicit and covered; pending edits are not silently overwritten. | Deterministic fake-remote conflict tests |
| AC5 | Cart rejects invalid quantities and computes totals deterministically; the default cart is in-memory, and the Drift implementation appears only when `commerce-persistence` is selected. | Domain tests plus generated combination checks |
| AC6 | Checkout handles empty cart, loading, failure and success; request has no client-supplied price/card fields and server quote is displayed as authoritative. | Contract/widget tests inspecting request and states |
| AC7 | Unselected modules add no files/dependencies/permissions; all selected generated combinations format, analyze, test and build. Existing presets remain unchanged. | Generator tests; static and built matrices; permission report |
| AC8 | Documentation accurately describes TTL, invalidation, local/offline behavior, retry/idempotency and conflict limits; security/license/dependency reports pass. | Docs review/link check, secret scan, OSV, license inventory |

Not claimed: background synchronization, multi-device conflict resolution, guaranteed server consistency, production catalog/pricing, payment processing, encrypted database contents, or live backend checkout.
