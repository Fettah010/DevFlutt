# v0.8.0 research — Android platform services

Checked 2026-10-28. This research supports only the v0.8.0 platform-services
milestone; package versions and Play behavior must be rechecked at the release gate.

| Question | Options | Evidence and finding | Decision and validation |
|---|---|---|---|
| How should deferrable work be scheduled? | Android Jetpack WorkManager via `workmanager`; a custom Kotlin channel; a Dart timer. | Android recommends WorkManager for work that must survive app exit/reboot; constraints and retries are supported, but scheduling is deferrable, not exact. `workmanager` 0.10.10 (published 2026-09-07) supports Dart >=3.5 and Flutter >=3.38; its package documents an Android implementation and MIT license. Resolved source `Workmanager.executeTask` accepts `Future<bool>` and returns that result to the platform: `true` completes and `false` requests retry; there is no distinct terminal-failure outcome. The custom channel duplicates plugin/platform behavior; an in-process timer cannot survive process death. [Android WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent), [package](https://pub.dev/packages/workmanager), [quick start](https://docs.page/fluttercommunity/flutter_workmanager/quickstart). | Use `workmanager` in an opt-in Android-only module. Keep callback input free of secrets and do not promise exact execution. Model only the supported success/retry outcomes and document that terminal failure needs an application policy. Verify API/build compatibility, fake-backed constraints/retry tests, and an Android emulator smoke; recheck the resolved dependency tree and license inventory before acceptance. |
| How should local notifications and taps be handled? | Android channel code; `flutter_local_notifications`; a push SDK. | Android 13+ requires `POST_NOTIFICATIONS`; new installs have notifications off until permission is granted, and apps targeting API 33+ choose when to request it. `flutter_local_notifications` 22.3.3 (published 2026-10-25) supports Dart ^3.10 and Flutter >=3.38.1, supports Android channels/permission queries and foreground/background/terminated tap handling, and is BSD-3-Clause. It is local notification functionality, not a push provider. [Android permission guidance](https://developer.android.com/develop/ui/compose/notifications/notification-permission), [package](https://pub.dev/packages/flutter_local_notifications), [license](https://pub.dev/packages/flutter_local_notifications/license). | Use the package in an opt-in Android-only `local-notifications` module. Declare `POST_NOTIFICATIONS` only for this selection; prompt only after a user action; route validated notification targets through the app router for warm and cold starts. Do not add a push provider. Verify denied/granted and tap behavior on emulator; reserve real-device confirmation for V3. |
| How should in-app updates work? | The official Play Core API through a Flutter plugin; a custom Kotlin bridge; an update-banner-only package. | Google Play provides flexible/immediate update flows for installed Android apps; availability depends on Play distribution and cannot be proven from a normal local build. The `in_app_update` plugin 5.0.0 (published 2026-07-04) wraps the official API, supports Dart ^3.12 and Flutter >=3.44, and is MIT-licensed. Its documentation says a Play-installed build is needed for live testing. The official Play flow is Android-only; unsupported/errors need an explicit fallback. [Android in-app updates](https://developer.android.com/guide/playcore/in-app-updates), [plugin](https://pub.dev/packages/in_app_update), [plugin test guidance](https://developer.android.com/guide/playcore/in-app-updates/test). | Use `in_app_update` behind an app-owned update contract and `url_launcher` 6.3.3 (Flutter Authors, BSD-3-Clause) for the Play Store HTTPS fallback. Map unavailable, canceled, failed, unsupported, and completed outcomes; test the mapping with fakes and record a Play internal-test run as an owner action. |
| Which target platforms are supported in this milestone? | Add platform-specific iOS substitutes now; support both platforms through plugins; reject unsupported module/platform combinations. | Workmanager's iOS integration has separate background modes, lifecycle, plugin-registration, and minimum-deployment setup; Play updates have no iOS equivalent. The notification plugin supports iOS, but its permission/lifecycle path is distinct. The milestone is explicitly Android platform services and requires that iOS generation not silently emit broken native code. [Workmanager iOS setup](https://docs.page/fluttercommunity/flutter_workmanager/quickstart), [Play update support](https://developer.android.com/guide/playcore/in-app-updates). | Keep these three modules Android-only in v0.8. Add generator validation that rejects a requested platform set not supported by every selected module, before writing files. iOS substitutes and push-provider integrations remain out of scope. |
| Is a new ADR required? | Add a provider ADR; use the existing architecture; defer all choices. | The existing architecture and app-owned adapter boundaries remain unchanged. The roadmap's ADR-009 is about updating already-generated template copies, not Android in-app app updates. Package comparisons, exact versions, and trade-offs are recorded here and in the v0.8 plan. | No ADR is required for these bounded plugin choices. Revisit only if a plugin cannot meet the acceptance criteria or a public contract must change; do not silently change the accepted architecture. |

Dependency transitive counts, resolved licenses, Android SDK compatibility, and
vulnerability findings are not inferred from package pages. They must be recorded
from the generated-project lockfiles, `tool/module_dependency_audit`, and the
repository's license/OSV gates before the V2 milestone gate.
